# Agent evals

Tests B, C and D from the design spec (§13.2), run through **your own signed-in Claude Code** on your Claude plan: never an API key, never in CI, and only when you start them.

| Test | What it checks | Cases |
|---|---|---|
| B — consistency | Fresh sessions each add a feature to Larder (`fixtures/react-contract-app`), a page to Kitepost (`fixtures/plain-contract-site`), or a feature to Maktaba, a Flutter app (`fixtures/flutter-contract-app`), to Rafiq, a Jetpack Compose app (`fixtures/compose-contract-app`), to Dukkan, an Expo app (`fixtures/rn-contract-app`), or to Qahwa, a SwiftUI app (`fixtures/swiftui-contract-app`, on a Mac), and stay inside its design guide | `b-settings`, `b-search`, `b-profile`, `b-notifications`, `b-checkout`, `b-plain`, `b-flutter-reserve`, `b-flutter-search`, `b-compose-reminder`, `b-compose-stats`, `b-rn-orders`, `b-rn-favourites`, `b-swiftui-orders`, `b-swiftui-rewards` |
| C — review accuracy | Reviews of the seeded app (`fixtures/react-seeded-app`, 23 planted problems), the seeded site (`fixtures/plain-seeded-site`, 18), the seeded Flutter app (`fixtures/flutter-seeded-app`, 16), the seeded Compose app (`fixtures/compose-seeded-app`, 15), the seeded Expo app (`fixtures/rn-seeded-app`, 14) and the seeded SwiftUI app (`fixtures/swiftui-seeded-app`, 16, on a Mac) find what was planted | `c-review`, `c-plain`, `c-flutter`, `c-compose`, `c-rn`, `c-swiftui` |
| D — zero accounts | A new app from each brief (`fixtures/briefs/`: three web apps, Sahm, a Flutter app, Nabta, a Compose app, Rihla, an Expo app, and Masar, a SwiftUI app on a Mac, all four in English and Arabic), plus B and C, all with no design sources connected | `d-stride`, `d-ledgerly`, `d-bloom`, `d-sahm`, `d-nabta`, `d-rihla`, `d-masar` |

## Before you start

- Claude Code, signed in with your Claude account: `claude auth status` shows `"authMethod": "claude.ai"`. The evals never use an API key.
- Bun (this repository's tool), git, and Node.js 20.9 or later with npm.
- Chrome or Edge for tests C and D on the web, for `b-plain`, and for the React Native cases (`b-rn-orders`, `b-rn-favourites`, `c-rn`, `d-rihla`), whose screens are drawn through Expo's web target. If you have neither, `motif browser install` downloads a private browser of about 120 MB (about 300 MB on disk); the runner never runs it for you. The Flutter, Compose and SwiftUI cases don't need one: Flutter, Robolectric and the iOS simulator draw their screens.
- Flutter 3.27 or later on the `PATH` for the Flutter cases (`b-flutter-reserve`, `b-flutter-search`, `c-flutter`, `d-sahm`; [how to install it](https://docs.flutter.dev/get-started/install)). Without it, a run that includes them stops before starting and lists the other cases to run instead.
- A JDK 17 or later and the Android SDK for the Compose cases (`b-compose-reminder`, `b-compose-stats`, `c-compose`, `d-nabta`): `motif doctor` shows what it finds (`JAVA_HOME`, the `PATH`, or Android Studio's own JDK; `ANDROID_HOME`, `ANDROID_SDK_ROOT` or Android Studio's default folder). Without them, a run that includes the Compose cases stops before starting, says what's missing in doctor's words and lists the web and Expo cases to run instead. Each Compose case folder gets a `local.properties` pointing at your SDK (never committed), and the first screenshots download Robolectric's Android libraries (a few hundred MB).
- A Mac with Xcode 16 or later and an iOS simulator for the SwiftUI cases (`b-swiftui-orders`, `b-swiftui-rewards`, `c-swiftui`, `d-masar`): SwiftUI apps build and draw only on macOS. Elsewhere the runner skips them, says why, and runs the other cases you chose (a run of SwiftUI cases alone doesn't start). Each is recorded as skipped with the reason: the report shows it, the verdicts leave it out of the count and name it ("All 12 cases run passed; b-swiftui-orders and b-swiftui-rewards were skipped (they need a Mac)."), and the exit code agrees, so a full run off a Mac can pass. Resuming that run on a Mac (`--resume <run>`) runs the skipped cases there, finishing the same record; one whose session had already finished on a Mac (its grading paused or failed) keeps its folder and session while skipped, and is graded there, not run again. On a Mac without Xcode or a simulator, a run that includes them stops before starting, says what's missing in `motif doctor`'s words and lists the other cases to run instead; on a Mac, a missing Flutter or Android SDK offers the SwiftUI cases among those others.
- Time and usage. Each case is a full Claude Code session: up to 90 minutes for B and C cases on the web, 2 hours on Flutter, Compose and SwiftUI (every screenshot builds the app) and on Expo (its web target's first bundle takes minutes), 3 hours for D cases, plus installing and building the app. A full run is 27 sessions (23 off a Mac) and uses a large share of your plan's usage, so you may prefer one test at a time.

## Running

From the repository root:

```bash
bun tests/evals/run.ts --list                  # the 27 cases
bun tests/evals/run.ts --dry-run --tests B     # each prompt and the exact Claude Code command, without running anything
bun tests/evals/run.ts --tests B               # one test
bun tests/evals/run.ts --cases b-search,c-review
bun tests/evals/run.ts --cases b-flutter-reserve,b-flutter-search,c-flutter,d-sahm   # the Flutter cases
bun tests/evals/run.ts --cases b-compose-reminder,b-compose-stats,c-compose,d-nabta   # the Compose cases
bun tests/evals/run.ts --cases b-rn-orders,b-rn-favourites,c-rn,d-rihla   # the React Native (Expo) cases
bun tests/evals/run.ts --cases b-swiftui-orders,b-swiftui-rewards,c-swiftui,d-masar   # the SwiftUI cases, on a Mac
bun tests/evals/run.ts                         # everything (off a Mac, everything but the SwiftUI cases)
```

| Option | What it does |
|---|---|
| `--tests B,C,D` · `--cases <id,…>` | Run only these |
| `--dry-run` | Show what would run; start nothing, write nothing |
| `--resume <run>` | Continue a run that stopped |
| `--regrade <run>` | Grade a finished run's B cases again with this checkout's new-component rule, from their saved diffs. Nothing else is run or changed, and the report says when it was re-graded |
| `--keep` | Keep each case's folder after grading (to look at the apps) |
| `--model <name>` · `--judge-model <name>` | The model for the sessions, and for test C's grader (default: your account's) |
| `--max-turns <n>` | Cap every case at n turns: a quick check that the runner works |
| `--work <folder>` | Where case folders go, one subfolder per run (default: `~/.motif-evals`, outside the temp folder, which macOS empties of files untouched for three days) |
| `--claude <path>` | The Claude Code program to use |

At the start of a run, the runner builds the motif tool and the Claude Code plugin from this checkout (`bun run build` and `bun run plugin` in `cli`), so the sessions test the code in front of you.

## What each session gets

- **A fresh folder** in `~/.motif-evals` (or `--work`): a copy of the fixture app with its packages installed (B, C: `npm ci` for Larder and Dukkan, `flutter pub get` for Maktaba, or a `local.properties` pointing at your Android SDK for Rafiq; Qahwa, a SwiftUI app with no packages, gets nothing), or an empty folder holding the brief as `brief.md` (D; Masar's also holds the project Xcode's iOS App template makes). Its temp folder (`TMP`, `TEMP`, `TMPDIR`) is in there too, so whatever a session writes to temp goes when the case's folder does; the grader gets one in its own folder.
- **Your Claude account only.** `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL` and the other-provider switches are left out of the session's environment, and a session that reports any API key stops the run.
- **None of your setup.** `--setting-sources project,local` leaves out your own settings, hooks, plugins, skills and agents; `--strict-mcp-config` with an empty list leaves out every MCP server (that's test D's "zero accounts"); only Motif's plugin is loaded, from `dist/claude-code`. The session's first event is checked for all of this (an API key, MCP servers, other plugins, your own skills or agents, tools outside the allowed list), and the run stops if anything is off, or if that first event is missing. A run won't start while a `CLAUDE.md` that every session would read sits in or above the case folders (or in `~/.claude/`): move it aside, or choose another `--work` folder. The default folder is in your home folder, so a `~/CLAUDE.md` stops it too.
- **Unattended, never bypassed.** `--permission-mode auto --permission-prompts none`: Claude Code's auto mode approves ordinary work and refuses risky actions, and nobody is asked. Refusals are listed in the report. If a session doesn't start in auto mode (some models don't support it), the run stops and says to choose another with `--model`. Sessions get only the tools a coding session needs (files, the shell, search, skills, subagents, their task list and the web); nothing that publishes pages, messages your other sessions, schedules work or leaves the folder. A session can't add MCP servers to your own coding agents: `motif connect` is turned off in its environment (`MOTIF_NO_CONNECT`), `claude mcp …` is denied, and after each session the runner compares your agents' MCP servers with what they were before (a session that changed them stops the run, naming what was added).
- **Gates off by instruction.** Each prompt starts a Motif command (`/motif:feature`, `/motif:review`, `/motif:init`) and adds "don't stop for approval", as a developer would.
- **No traces.** Sessions keep no transcript in Claude Code (`--no-session-persistence`), and `claude purge` removes Claude Code's state for each case folder afterwards. Case folders are deleted after grading unless you pass `--keep`. The grader (test C) works from a folder of its own and reads the app from there, so nothing a session left in the app (a `CLAUDE.md`, `.claude/` settings) reaches it.

## Usage limits and resuming

If your plan's usage limit is reached, the run pauses, says when the limit resets, and prints the command to continue:

```bash
bun tests/evals/run.ts --resume <run>
```

Ctrl+C works the same way. A case cut off mid-session, or one where Claude Code failed part-way (an API error, a crash), isn't graded and starts again from a fresh folder; cases already graded keep their results. If the limit is reached while test C is being graded, the review isn't repeated: its folder is kept and `--resume` grades it again. Resuming on a different commit is allowed, and the report says so.

## Results

Everything goes to `tests/evals/results/<run>/` (git-ignored; nothing is uploaded):

- `report.md`: the verdict for each test and a table of criteria for each case; `report.json` and `run.json` hold the same for tools.
- Per case: `session.jsonl` (every event of the session, to see exactly what Claude Code did), `diff.patch` (what it changed), `check.json`, `validate.json`, `build.log`, `typecheck.log` (on Flutter, `pub-get.log` and `analyze.log` instead of the last two; on Compose, `compile.log`; on SwiftUI, `xcodebuild.log`; on Expo, no `build.log`); for C, `review.json`, `review.md`, `audit.json`, `grading.json` and `judge.jsonl`; for D, the new app's `DESIGN.md`, `tokens.json`, `shot.json` and `shots/`.

The dollar figure in the report is Claude Code's own estimate at API prices, to show scale; your plan covers the usage.

Exit codes: `0` every case passed (Mac-only cases skipped off a Mac aside), `1` some case failed or couldn't be graded, `2` the run couldn't start (or a session wasn't isolated), `3` paused at the usage limit.

## How cases are graded

**B** (every case): the feature's page exists; `motif check` finds no problems and no warnings, with at most 2 `motif-ok` exceptions; `motif validate` passes; the app builds and type-checks; at most one new component, unless the others are named, written as they are, in lines the session added to `DESIGN.md` (a recorded design guide change; a guide saved with other line endings isn't counted as rewritten). A new component is a new `.tsx` or `.jsx` file anywhere under `src/` that draws something and isn't a route file, test or story. A file in a route folder (`src/app/…`) built from the app's own components is part of that screen, and a file that draws nothing (state shared through a context) isn't UI: neither counts, and the report names them. A route file that reuses none of the app's components still counts. On Kitepost (`b-plain`), a plain web site with nothing to build, the new page must load in `motif shot` with no page errors instead of building and type-checking, and a new component is a new `Component:` line in its CSS (rewriting an existing one's line doesn't count).

On Maktaba (`b-flutter-reserve`, `b-flutter-search`), the page exists when Motif's route discovery finds it among go_router's routes; `flutter pub get` then `flutter analyze --no-fatal-infos` stand for the type check (infos don't fail it; warnings and errors do, and so does a `flutter pub get` that fails); there's no build, and instead the new page must be drawn by `motif shot --routes <route> --sizes 390` with no errors. A new component is a public class the session adds under `lib/` that extends `StatelessWidget`, `StatefulWidget`, `ConsumerWidget`, `ConsumerStatefulWidget` or `HookWidget` (or the other hook widgets). A private class (`_Name`) is part of a screen, and the widget a route shows (what a `GoRoute`'s `builder:` returns, by `=>` or `return`, or the child of the page its `pageBuilder:` or a `ShellRoute`'s `pageBuilder:` makes; a `ShellRoute`'s `builder:` makes the navigation, a component, and a `LayoutBuilder`, `FutureBuilder` or other builder shows no page) is the page itself, as a React route file is: neither counts, and the report names them. Classes under `lib/design/` (Motif's theme code) and generated files never count, and a class the session moved from one file to another isn't new. The reserve flow is at `/reserve` rather than under `/books/`: go_router gives `/books/reserve` to the book page's `/books/:id` whenever the new route is listed after it.

On Rafiq (`b-compose-reminder` at `/reminders`, `b-compose-stats` at `/stats`), the screen exists when Motif's screen discovery lists its route (a Navigation Compose destination) or a `@Preview` named for it (`RemindersPreview` or `RemindersScreenPreview`). `./gradlew :app:compileDebugKotlin` stands for the type check (the wrapper's jar is started with the JDK `motif doctor` chooses, as `motif shot` does, because `gradlew.bat` breaks on some paths); there's no build, and instead the screen must be drawn by `motif shot --routes <route> --sizes 390` (or `--screen <preview>` when it exists only as a preview) with no errors. A new component is a public `@Composable` function the session adds under `ui/` that isn't a `@Preview`. A private one is part of a screen, and a screen's entry point (`*Screen`, with the `*Content` function beside it in the same file) is the page itself: neither counts, and the report names them. The generated theme (`ui/motif/`, or any file that starts with Motif's header) never counts, and a function the session moved from one file to another isn't new.

On Dukkan (`b-rn-orders`, `b-rn-favourites`), the screen exists when Motif's route discovery finds it among Expo Router's routes (`app/orders.tsx` is `/orders`); `npx tsc --noEmit` is the type check; there's no build, and instead the new screen must be drawn by `motif shot --routes <route> --sizes 390` (Expo's web target, in Chrome or Edge; the first bundle can take minutes) with no errors. A new component is an exported function component the session adds under `components/` that renders JSX. A route file under `app/` is a screen: its default export is the page itself, and its other components (private ones, or extra exports) are parts of it; a private component in a `components/` file is part of that component; a capitalised function that draws no JSX, and a new `_layout` file (navigation), aren't UI. Neither screens nor parts count, and the report names them. The generated theme (`design/`), state files, tests and stories never count, and a component the session moved from one file to another isn't new.

On Qahwa (`b-swiftui-orders`, `b-swiftui-rewards`; on a Mac), SwiftUI's screens have no address, so each prompt names the new screen's `#Preview` (`"Orders"`, `"Rewards history"`), and that is the case's page. The screen exists when Motif's screen discovery finds a `#Preview` titled for it (`Orders`, `Orders screen` or `Orders view`) or one that shows its type (`OrdersScreen` or `OrdersView`), or when the app declares that type and another file shows it (a navigation link, say), though then it can't be drawn on its own. `xcodebuild build` for any iOS simulator (`-destination "generic/platform=iOS Simulator"`, `CODE_SIGNING_ALLOWED=NO`, its DerivedData in the case's folder, never Xcode's own) stands for the type check, and a failed build names the compiler's first errors; there's no other build, and instead the preview must be drawn by `motif shot --screen <File.swift:line> --sizes 390` with no errors (nothing is drawn when there's no preview). A new component is a public or internal `View` struct the session adds at the top level of the app's Swift files (read from braces, so one under `#if DEBUG` is still top level). A private or `fileprivate` one, or one inside another type or an extension, is part of a screen, and a screen is the page itself: a `*Screen` or `*View` struct that the root's `WindowGroup`, a `NavigationStack` or `TabView`, a `NavigationLink` or `.navigationDestination`, or a sheet shows, or one only a `#Preview` shows when it's a `*Screen` or the case's own page (`OrdersView` for `"Orders"`); a row with a preview of its own (`OrderRowView`) is still a component. Neither parts nor screens count, and the report names them. The theme folder (`Design/`), any file that starts with Motif's header, tests, Motif's screenshot harness and `design/states/` never count, and a struct the session moved from one file to another isn't new.

**C**: the review writes a report in the review format (`design/reviews/*.json`) and changes nothing outside `design/`. Findings are matched to `seeded-issues.json` by category and place, following the seeded fixture's grading rules ([the app](../fixtures/react-seeded-app/README.md#how-a-grader-reads-the-list), [the site](../fixtures/plain-seeded-site/README.md#how-a-grader-reads-the-list), [the Flutter app](../fixtures/flutter-seeded-app/README.md#how-a-grader-reads-the-list), [the Compose app](../fixtures/compose-seeded-app/README.md#how-a-grader-reads-the-list), [the Expo app](../fixtures/rn-seeded-app/README.md#how-a-grader-reads-the-list), [the SwiftUI app](../fixtures/swiftui-seeded-app/README.md#how-a-grader-reads-the-list)); knock-on findings the list declares count as correct. Exact problems found at their file (or line) are matched by the runner alone; for judgement problems, and for exact problems a finding names only by screen, a model grader (one read-only Claude Code session, with [this rubric](rubric.md)) confirms which candidate findings describe each problem, and decides whether serious findings that match nothing are real or false. Pass: at least 90% of the exact problems (13 in the app, 11 in the site, 10 in the Flutter app, 10 in the Compose app, 10 in the Expo app and 11 in the SwiftUI app), at least 70% of the judgement problems (10, 7, 6, 5, 4 and 5), at most 10% of critical and major findings false. The SwiftUI app's screens are its root (`/`) and its previews (Menu, Drink, Loyalty card, Sign in), named so in `c-swiftui`'s prompt.

**D** (every brief): the new app (the folder with `DESIGN.md`) passes `motif validate` and `motif check` (at most 2 `motif-ok` exceptions); `DESIGN.md` has every section, each filled in; the app builds and type-checks; `/`, `/sign-in` and `/home` (`/trips` for Rihla) render in `motif shot` (status 200, no page errors). Sahm (`d-sahm`) is a Flutter app: after `flutter pub get`, `flutter analyze --no-fatal-infos` stands for the type check, there's no build, and the screens are drawn at 390 wide (`--sizes 390`). Nabta (`d-nabta`) is a Compose app: `./gradlew :app:compileDebugKotlin` is the type check (a new app with no Gradle wrapper fails it), there's no build, and the screens are drawn at 390 wide. Rihla (`d-rihla`) is an Expo app: the packages are installed when the session didn't, `npx tsc --noEmit` is the type check, there's no build, and its screens are drawn at 390 wide through Expo's web target. Masar (`d-masar`, on a Mac) is a SwiftUI app for iPhone. An Xcode project has no command-line starter and the SwiftUI guide says never to write one by hand, so its folder holds, beside the brief, the project Xcode's iOS App template makes (`fixtures/swiftui-starter-masar`: `Masar.xcodeproj`, object version 77 with a synchronized `Masar/` folder, iOS 17, Swift 5, and the template's `MasarApp.swift`, `ContentView.swift` and asset catalogue), and the brief says so; there are still no design sources. Its screens have no address, so the prompt asks for the welcome screen as the app's root view and `#Preview`s titled `Sign in` and `Home`: those three are drawn at 390 wide (`motif shot --audit --routes / --screen <File.swift:line,…> --sizes 390`, a preview the app lacks left out and reported as not captured), and `xcodebuild build`, as on Qahwa, is the type check, with no other build. Test D passes when the new apps pass and tests B and C pass, since every session runs with no MCP servers.

## Tests of the runner

`cli/test/evals-*.test.ts` run in CI with a stand-in for Claude Code (`cli/test/fixtures/evals/fake-claude.ts`) and stubbed installs and builds. They never start a real session, use your plan or reach the network.
