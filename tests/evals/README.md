## Before you start

- Claude Code, signed in with your Claude account: `claude auth status` shows `"authMethod": "claude.ai"`. On a machine you reach without a browser (a remote Mac), your account's own token from `claude setup-token`, given as `CLAUDE_CODE_OAUTH_TOKEN`, shows `"oauth_token"` and is accepted too. The evals never use an API key.
- Bun (this repository's tool), git, and Node.js 20.9 or later with npm. The Vue cases (`b-vue-history`, `b-vue-settings`, `c-vue`, `d-darb`) need Node.js 20.19 or later, or 22.12 or later on Node 22, for Bustan's Vite 8: with an older one, a run that includes them stops before starting and lists the other cases to run instead. The Svelte cases on Adawat (`b-svelte-history`, `b-svelte-settings`, `c-svelte`) need the same, for its Vite 8. `d-nuzha` and `a-nuzha` make a new app with `npx sv create`, which installs SvelteKit 3, so they need Node.js 22.17 or later: on an older one the run stops before starting, says so and lists the other cases to run instead. The Angular cases on Ataa (`b-angular-history`, `b-angular-settings`, `c-angular`) need Angular 21's Node.js: 20.19 or later on Node 20, 22.12 or later on Node 22, or 24 or later (Node 23 isn't one); on another, a run that includes them stops before starting and lists the other cases to run instead. `d-sanad` and `a-sanad` make a new app with `ng new`, which installs the latest Angular (22), so they need Angular 22's Node.js: 22.22.3 or later on Node 22, 24.15 or later on Node 24, or 26 or later. On another, a run that includes it stops before starting, says so and lists the other cases to run instead.
- Chrome or Edge for tests C and D on the web, for `b-plain`, for the React Native cases (`b-rn-orders`, `b-rn-favourites`, `c-rn`, `d-rihla`), whose screens are drawn through Expo's web target, and for the Vue, Svelte and Angular cases (`b-vue-history`, `b-vue-settings`, `c-vue`, `d-darb`, `b-svelte-history`, `b-svelte-settings`, `c-svelte`, `d-nuzha`, `b-angular-history`, `b-angular-settings`, `c-angular`, `d-sanad`), whose pages are drawn at 390 and 1440 wide. If you have neither, `motif browser install` downloads a private browser of about 120 MB (about 300 MB on disk); the runner never runs it for you. The Flutter, Compose and SwiftUI cases don't need one: Flutter, Robolectric and the iOS simulator draw their screens.
- Flutter 3.27 or later on the `PATH` for the Flutter cases (`b-flutter-reserve`, `b-flutter-search`, `c-flutter`, `d-sahm`; [how to install it](https://docs.flutter.dev/get-started/install)). Without it, a run that includes them stops before starting and lists the other cases to run instead.
- A JDK 17 or later and the Android SDK for the Compose cases (`b-compose-reminder`, `b-compose-stats`, `c-compose`, `d-nabta`): `motif doctor` shows what it finds (`JAVA_HOME`, the `PATH`, or Android Studio's own JDK; `ANDROID_HOME`, `ANDROID_SDK_ROOT` or Android Studio's default folder). Without them, a run that includes the Compose cases stops before starting, says what's missing in doctor's words and lists the web and Expo cases to run instead. Each Compose case folder gets a `local.properties` pointing at your SDK (never committed), and the first screenshots download Robolectric's Android libraries (a few hundred MB).
- A Mac with Xcode 16 or later and an iOS simulator for the SwiftUI cases (`b-swiftui-orders`, `b-swiftui-rewards`, `c-swiftui`, `d-masar`): SwiftUI apps build and draw only on macOS. Elsewhere the runner skips them, says why, and runs the other cases you chose (a run of SwiftUI cases alone doesn't start). Each is recorded as skipped with the reason: the report shows it, the verdicts leave it out of the count and name it ("All 12 cases run passed; b-swiftui-orders and b-swiftui-rewards were skipped (they need a Mac)."), and the exit code agrees, so a full run off a Mac can pass. Resuming that run on a Mac (`--resume <run>`) runs the skipped cases there, finishing the same record; one whose session had already finished on a Mac (its grading paused or failed) keeps its folder and session while skipped, and is graded there, not run again. On a Mac without Xcode or a simulator, a run that includes them stops before starting, says what's missing in `motif doctor`'s words and lists the other cases to run instead; on a Mac, a missing Flutter or Android SDK offers the SwiftUI cases among those others.
- Time and usage. Each case is a full Claude Code session: up to 90 minutes for B and C cases on the web, 2 hours on Flutter, Compose and SwiftUI (every screenshot builds the app), on Expo (its web target's first bundle takes minutes), on Vue, on Svelte and on Angular, 3 hours for D and A cases, plus installing and building the app. A full run is 49 sessions (44 off a Mac) and uses a large share of your plan's usage, so you may prefer one test at a time.

## Running

From the repository root:

```bash
bun tests/evals/run.ts --list                  # the 49 cases
bun tests/evals/run.ts --dry-run --tests B     # each prompt and the exact Claude Code command, without running anything
bun tests/evals/run.ts --tests B               # one test
bun tests/evals/run.ts --tests D,A             # each brief with Motif, then without (a-x runs right after d-x)
bun tests/evals/run.ts --cases b-search,c-review
bun tests/evals/run.ts --cases b-flutter-reserve,b-flutter-search,c-flutter,d-sahm   # the Flutter cases
bun tests/evals/run.ts --cases b-compose-reminder,b-compose-stats,c-compose,d-nabta   # the Compose cases
bun tests/evals/run.ts --cases b-rn-orders,b-rn-favourites,c-rn,d-rihla   # the React Native (Expo) cases
bun tests/evals/run.ts --cases b-vue-history,b-vue-settings,c-vue,d-darb   # the Vue cases
bun tests/evals/run.ts --cases b-svelte-history,b-svelte-settings,c-svelte,d-nuzha   # the Svelte cases (Node.js 22.17 or later for d-nuzha)
bun tests/evals/run.ts --cases b-angular-history,b-angular-settings,c-angular,d-sanad   # the Angular cases (Angular 22's Node.js for d-sanad)
bun tests/evals/run.ts --cases b-swiftui-orders,b-swiftui-rewards,c-swiftui,d-masar   # the SwiftUI cases, on a Mac
bun tests/evals/run.ts                         # everything (off a Mac, everything but the SwiftUI cases)
```

| Option | What it does |
|---|---|
| `--tests A,B,C,D` · `--cases <id,…>` | Run only these |
| `--dry-run` | Show what would run; start nothing, write nothing |
| `--resume <run>` | Continue a run that stopped |
| `--regrade <run>` | Grade a finished run's B cases again with this checkout's new-component rule, from their saved diffs. Nothing else is run or changed, and the report says when it was re-graded |
| `--keep` | Keep each case's folder after grading (to look at the apps). With A chosen, a brief's `d-*` and `a-*` folders are kept anyway until both are graded and Test A's step after them has run |
| `--model <name>` · `--judge-model <name>` | The model for the sessions, and for test C's grader (default: your account's) |
| `--max-turns <n>` | Cap every case at n turns: a quick check that the runner works |
| `--work <folder>` | Where case folders go, one subfolder per run (default: `~/.motif-evals`, outside the temp folder, which macOS empties of files untouched for three days) |
| `--claude <path>` | The Claude Code program to use |

At the start of a run, the runner builds the motif tool and the Claude Code plugin from this checkout (`bun run build` and `bun run plugin` in `cli`), so the sessions test the code in front of you.

## What each session gets

- **A fresh folder** in `~/.motif-evals` (or `--work`): a copy of the fixture app with its packages installed (B, C: `npm ci` for Larder and Dukkan, `flutter pub get` for Maktaba, or a `local.properties` pointing at your Android SDK for Rafiq; Qahwa, a SwiftUI app with no packages, gets nothing), or an empty folder holding the brief as `brief.md` (D and A; Masar's also holds the project Xcode's iOS App template makes). Its temp folder (`TMP`, `TEMP`, `TMPDIR`) is in there too, so whatever a session writes to temp goes when the case's folder does; the grader gets one in its own folder.
- **Your Claude account only.** `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL` and the other-provider switches are left out of the session's environment, and a session that reports any API key stops the run.
- **None of your setup.** `--setting-sources project,local` leaves out your own settings, hooks, plugins, skills and agents; `--strict-mcp-config` with an empty list leaves out every MCP server (that's test D's "zero accounts"); only Motif's plugin is loaded, from `dist/claude-code`, and Test A's `a-*` sessions load no plugin at all (their first event must list none but Claude Code's own built-in ones, Motif's included, and their environment has no `MOTIF_` variables). Nothing in their arguments names Motif either: no plugin folder, no rule about `motif connect` (they have no Motif to connect), and their empty MCP list is a file in their own case folder rather than in this checkout's results. Their folders are under `--work`, so choose one whose path doesn't name Motif for a run with Test A. The session's first event is checked for all of this (an API key, MCP servers, other plugins, your own skills or agents, tools outside the allowed list), and the run stops if anything is off, or if that first event is missing. A run won't start while a `CLAUDE.md` that every session would read sits in or above the case folders (or in `~/.claude/`): move it aside, or choose another `--work` folder. The default folder is in your home folder, so a `~/CLAUDE.md` stops it too.
- **Unattended, never bypassed.** `--permission-mode auto --permission-prompts none`: Claude Code's auto mode approves ordinary work and refuses risky actions, and nobody is asked. Refusals are listed in the report. If a session doesn't start in auto mode (some models don't support it), the run stops and says to choose another with `--model`. Sessions get only the tools a coding session needs (files, the shell, search, skills, subagents, their task list and the web); nothing that publishes pages, messages your other sessions, schedules work or leaves the folder. A session can't add MCP servers to your own coding agents: `motif connect` is turned off in its environment (`MOTIF_NO_CONNECT`), `claude mcp …` is denied, and after each session the runner compares your agents' MCP servers with what they were before (a session that changed them stops the run, naming what was added).
- **Gates off by instruction.** Each prompt starts a Motif command (`/motif:feature`, `/motif:review`, `/motif:init`) and adds "don't stop for approval", as a developer would. Test A's prompt is its D brief's with every mention of Motif taken out (no `/motif:init`; "it has the answers to any questions you'd ask"), plus "Make it look and work well.", and the same unattended words, which name nothing of Motif's.
- **No traces.** Sessions keep no transcript in Claude Code (`--no-session-persistence`), and `claude purge` removes Claude Code's state for each case folder afterwards. Case folders are deleted after grading unless you pass `--keep`; with A chosen, a brief's two folders go together, once both are graded and Test A's step after them has run. The grader (test C) works from a folder of its own and reads the app from there, so nothing a session left in the app (a `CLAUDE.md`, `.claude/` settings) reaches it.

## Usage limits and resuming

If your plan's usage limit is reached, the run pauses, says when the limit resets, and prints the command to continue:

```bash
bun tests/evals/run.ts --resume <run>
```

Ctrl+C works the same way. A case cut off mid-session, or one where Claude Code failed part-way (an API error, a crash), isn't graded and starts again from a fresh folder; cases already graded keep their results. If the limit is reached while test C is being graded, the review isn't repeated: its folder is kept and `--resume` grades it again. Resuming on a different commit is allowed, and the report says so.

## Results

Everything goes to `tests/evals/results/<run>/` (git-ignored; nothing is uploaded):

- `report.md`: the verdict for each test and a table of criteria for each case; `report.json` and `run.json` hold the same for tools.
- Per case: `session.jsonl` (every event of the session, to see exactly what Claude Code did), `diff.patch` (what it changed), `check.json`, `validate.json`, `build.log`, `typecheck.log` (on Flutter, `pub-get.log` and `analyze.log` instead of the last two; on Compose, `compile.log`; on SwiftUI, `xcodebuild.log`; on Expo, no `build.log`; on Vue and Svelte, `build.log` and `typecheck.log` as on the web; on Angular, `build.log`, and `typecheck.log` with the type errors read from it); for C, `review.json`, `review.md`, `audit.json`, `grading.json` and `judge.jsonl`; for D, the new app's `DESIGN.md`, `tokens.json`, `shot.json` and `shots/`.

The dollar figure in the report is Claude Code's own estimate at API prices, to show scale; your plan covers the usage.

Exit codes: `0` every case passed (Mac-only cases skipped off a Mac aside; an `a-*` case only needs to be graded, since an app built without Motif that fails is scored by Test A, not as the run's failure), `1` some case failed or couldn't be graded, `2` the run couldn't start (or a session wasn't isolated), `3` paused at the usage limit.

## How cases are graded

**B** (every case): the feature's page exists; `motif check` finds no problems and no warnings, with at most 2 `motif-ok` exceptions; `motif validate` passes; the app builds and type-checks; at most one new component, unless the others are named, written as they are, in lines the session added to `DESIGN.md` (a recorded design guide change; a guide saved with other line endings isn't counted as rewritten). A new component is a new `.tsx` or `.jsx` file anywhere under `src/` that draws something and isn't a route file, test or story. A file in a route folder (`src/app/…`) built from the app's own components is part of that screen, and a file that draws nothing (state shared through a context) isn't UI: neither counts, and the report names them. A route file that reuses none of the app's components still counts. On Kitepost (`b-plain`), a plain web site with nothing to build, the new page must load in `motif shot` with no page errors instead of building and type-checking, and a new component is a new `Component:` line in its CSS (rewriting an existing one's line doesn't count).

On Maktaba (`b-flutter-reserve`, `b-flutter-search`), the page exists when Motif's route discovery finds it among go_router's routes; `flutter pub get` then `flutter analyze --no-fatal-infos` stand for the type check (infos don't fail it; warnings and errors do, and so does a `flutter pub get` that fails); there's no build, and instead the new page must be drawn by `motif shot --routes <route> --sizes 390` with no errors. A new component is a public class the session adds under `lib/` that extends `StatelessWidget`, `StatefulWidget`, `ConsumerWidget`, `ConsumerStatefulWidget` or `HookWidget` (or the other hook widgets). A private class (`_Name`) is part of a screen, and the widget a route shows (what a `GoRoute`'s `builder:` returns, by `=>` or `return`, or the child of the page its `pageBuilder:` or a `ShellRoute`'s `pageBuilder:` makes; a `ShellRoute`'s `builder:` makes the navigation, a component, and a `LayoutBuilder`, `FutureBuilder` or other builder shows no page) is the page itself, as a React route file is: neither counts, and the report names them. Classes under `lib/design/` (Motif's theme code) and generated files never count, and a class the session moved from one file to another isn't new. The reserve flow is at `/reserve` rather than under `/books/`: go_router gives `/books/reserve` to the book page's `/books/:id` whenever the new route is listed after it.

On Rafiq (`b-compose-reminder` at `/reminders`, `b-compose-stats` at `/stats`), the screen exists when Motif's screen discovery lists its route (a Navigation Compose destination) or a `@Preview` named for it (`RemindersPreview` or `RemindersScreenPreview`). `./gradlew :app:compileDebugKotlin` stands for the type check (the wrapper's jar is started with the JDK `motif doctor` chooses, as `motif shot` does, because `gradlew.bat` breaks on some paths); there's no build, and instead the screen must be drawn by `motif shot --routes <route> --sizes 390` (or `--screen <preview>` when it exists only as a preview) with no errors. A new component is a public `@Composable` function the session adds under `ui/` that isn't a `@Preview`. A private one is part of a screen, and a screen's entry point (`*Screen`, with the `*Content` function beside it in the same file) is the page itself: neither counts, and the report names them. The generated theme (`ui/motif/`, or any file that starts with Motif's header) never counts, and a function the session moved from one file to another isn't new.

On Dukkan (`b-rn-orders`, `b-rn-favourites`), the screen exists when Motif's route discovery finds it among Expo Router's routes (`app/orders.tsx` is `/orders`); `npx tsc --noEmit` is the type check; there's no build, and instead the new screen must be drawn by `motif shot --routes <route> --sizes 390` (Expo's web target, in Chrome or Edge; the first bundle can take minutes) with no errors. A new component is an exported function component the session adds under `components/` that renders JSX. A route file under `app/` is a screen: its default export is the page itself, and its other components (private ones, or extra exports) are parts of it; a private component in a `components/` file is part of that component; a capitalised function that draws no JSX, and a new `_layout` file (navigation), aren't UI. Neither screens nor parts count, and the report names them. The generated theme (`design/`), state files, tests and stories never count, and a component the session moved from one file to another isn't new.

On Bustan (`b-vue-history` at `/history`, `b-vue-settings` at `/settings`), the page exists when Motif's route discovery finds it among Vue Router's routes (`discoverVueRoutes`); `npx vue-tsc --noEmit` is the type check and `npm run build` the build, and the new page must also be drawn by `motif shot --routes <route> --sizes 390,1440` (in Chrome or Edge) with no errors. A new component is a new `.vue` file under `components/` that has a template; a `.vue` file under `views/` or `pages/` is a screen (the page itself) and a new layout is navigation, so neither counts, and a component the session moved isn't new. The generated theme (`src/styles/`, `src/design/`) is CSS and TypeScript, never a `.vue` file, so it never counts.

On Adawat (`b-svelte-history` at `/history`, `b-svelte-settings` at `/settings`), the page exists when Motif's route discovery finds it among SvelteKit's file routes (`discoverSvelteRoutes`: `src/routes/history/+page.svelte` is `/history`); `npm run build` is the build and `npx svelte-check --fail-on-warnings` the type check (run after the build, which brings SvelteKit's generated types up to date; warnings fail it too), and the new page must also be drawn by `motif shot --routes <route> --sizes 390,1440` (in Chrome or Edge) with no errors. A new component is a new `.svelte` file with markup under `src/lib/` (`$lib`), in a `components/` folder, or beside a route; a `+page.svelte` is a screen (the page itself), `+layout.svelte` and `+error.svelte` are navigation, and a file with no markup draws nothing, so none of those count, and a component the session moved isn't new. The generated theme (`src/lib/styles/`, `src/lib/design/`) is CSS and TypeScript, never a `.svelte` file, so it never counts.

On Ataa (`b-angular-history` at `/history`, `b-angular-settings` at `/settings`), the page exists when Motif's route discovery lists it among the routes given to `provideRouter` (`discoverAngularRoutes`; under a hash router it is listed as `/#/history`, and is compared and drawn as listed). `npm run build` (`ng build`) is the build and the type check: it type-checks the TypeScript and, in strict mode, the templates, so no second command is run, and the type check fails when the build's output reports TypeScript or template errors (`TS2322`, `NG8002`; a template's type error comes as TypeScript's, such as `TS2339` with "Error occurs in the template of component …"), read with ng build's colour codes taken out. The new page must also be drawn by `motif shot --routes <route> --sizes 390,1440` (in Chrome or Edge) with no errors. A new component is an `@Component` class in a `.ts` file the session adds under `src/app/`; one the routes show (by `component:`, or by `loadComponent`'s `.then(m => m.X)`, or as the default export of the file it imports) is a screen (the page itself), so it doesn't count, and neither do services, directives, pipes, tests or a component the session moved. The generated theme (`src/styles/`, `src/app/design/`) has no components, so it never counts.

A type error is counted once. Bustan's build script runs `vue-tsc` before `vite build`, so a type error fails both; when the build stopped at TypeScript errors with no bundler output after them, only the type check fails and the build isn't counted again (a build that fails for its own reasons still counts). The rule is the same for any web app whose build script type-checks first: React's `tsc -b && vite build` (a new React or Vue app in test D) too. Adawat's build doesn't type-check. On Angular the build is the type check, so when type errors are all that stopped it, only the type check fails; a build that also failed for other reasons fails both.

On Qahwa (`b-swiftui-orders`, `b-swiftui-rewards`; on a Mac), SwiftUI's screens have no address, so each prompt names the new screen's `#Preview` (`"Orders"`, `"Rewards history"`), and that is the case's page. The screen exists when Motif's screen discovery finds a `#Preview` titled for it (`Orders`, `Orders screen` or `Orders view`) or one that shows its type (`OrdersScreen` or `OrdersView`), or when the app declares that type and another file shows it (a navigation link, say), though then it can't be drawn on its own. `xcodebuild build` for any iOS simulator (`-destination "generic/platform=iOS Simulator"`, `CODE_SIGNING_ALLOWED=NO`, its DerivedData in the case's folder, never Xcode's own) stands for the type check, and a failed build names the compiler's first errors; there's no other build, and instead the preview must be drawn by `motif shot --screen <File.swift:line> --sizes 390` with no errors (nothing is drawn when there's no preview). A new component is a public or internal `View` struct the session adds at the top level of the app's Swift files (read from braces, so one under `#if DEBUG` is still top level). A private or `fileprivate` one, or one inside another type or an extension, is part of a screen, and a screen is the page itself: a `*Screen` or `*View` struct that the root's `WindowGroup`, a `NavigationStack` or `TabView`, a `NavigationLink` or `.navigationDestination`, or a sheet shows, or one only a `#Preview` shows when it's a `*Screen` or the case's own page (`OrdersView` for `"Orders"`); a row with a preview of its own (`OrderRowView`) is still a component. Neither parts nor screens count, and the report names them. The theme folder (`Design/`), any file that starts with Motif's header, tests, Motif's screenshot harness and `design/states/` never count, and a struct the session moved from one file to another isn't new.

**C**: the review writes a report in the review format (`design/reviews/*.json`) and changes nothing outside `design/`. Findings are matched to `seeded-issues.json` by category and place, following the seeded fixture's grading rules ([the app](../fixtures/react-seeded-app/README.md#how-a-grader-reads-the-list), [the site](../fixtures/plain-seeded-site/README.md#how-a-grader-reads-the-list), [the Flutter app](../fixtures/flutter-seeded-app/README.md#how-a-grader-reads-the-list), [the Compose app](../fixtures/compose-seeded-app/README.md#how-a-grader-reads-the-list), [the Expo app](../fixtures/rn-seeded-app/README.md#how-a-grader-reads-the-list), [the Vue app](../fixtures/vue-seeded-app/README.md#how-a-grader-reads-the-list), [the Svelte app](../fixtures/svelte-seeded-app/README.md#how-a-grader-reads-the-list), [the Angular app](../fixtures/angular-seeded-app/README.md#how-a-grader-reads-the-list), [the SwiftUI app](../fixtures/swiftui-seeded-app/README.md#how-a-grader-reads-the-list)); knock-on findings the list declares count as correct. Once a brief's `d-*` and `a-*` are both graded, both apps' starter screens are shot again into pairs (Part 4 §5, `pairs.ts`): the same `motif shot --routes <the screens> --sizes <390,1440 for a web app, 390 for Flutter, Compose, Expo and SwiftUI> --out <a temporary folder>` for each app (left to right, in English; no `--rtl`, `--variant` or `--audit`; motif shot always takes light and dark, and only the light screenshots are kept). What each shot answered is kept as `pair-shots.json` in its case's results. If the step fails, both folders are kept and `--resume` runs it again (the run records each brief's step in `run.json`'s `pairs`).
