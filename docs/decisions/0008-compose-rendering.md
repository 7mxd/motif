# 0008 — Rendering Compose screens

- Date: 2026-10-20
- Status: Accepted
- Context: `motif shot` must show a Jetpack Compose app's screens the way people see them, in every size, light and dark, and right to left, on any developer's machine and in CI, without an emulator and without editing the app's build files. This spike (plan 2F, Task 8) checked on Windows 11 whether the JVM can draw `cli/test/fixtures/compose-min` with its real fonts: the Android Studio "Empty Activity" template grown to two screens in a Navigation Compose graph, three previews (one private), English and Arabic strings, and a bundled Noto Naskh Arabic in `res/font`. It can, with Robolectric. The harness skeleton is `cli/src/stacks/compose/harness/` (the Kotlin test and the Gradle init script), and its runner is `cli/src/stacks/compose/harness.ts`. `cli/test/compose-render.test.ts` draws the `mobile` size in light and dark from a path with a space and an `&` in it. The other sizes, Arabic, routes, previews, variants, Google fonts and Remove animations were rendered by hand during the spike and checked by eye; Task 9's end-to-end test covers them.

## Decisions

1. **Screens are drawn by Robolectric 4.17 with native graphics, from a JUnit test that Gradle runs as one of the app's unit tests.** The test is `dev.motif.shot.MotifShotTest` (`@RunWith(RobolectricTestRunner::class)`, `@GraphicsMode(NATIVE)`, `@Config(sdk = [35])`), with `createEmptyComposeRule()`. It runs the real Android framework (Android 15's `android-all-instrumented` jar), so resources, qualifiers, locale, night mode, activities and Navigation behave as on a device, and ATF can audit the same view tree (Task 10).
   - **Robolectric SDK 35.** It is the `compileSdk` floor and runs on the JDK 17 floor (proven). The app's own `compileSdk` and `targetSdk` can be higher (the fixture's are 36); a check like `SDK_INT >= 36` then takes the older branch. SDK 36 wasn't tried.
   - **A PNG is the window as Robolectric's `PixelCopy` draws it.** The harness idles the main looper, calls `compose.waitForIdle()`, then `PixelCopy.request(window, bitmap, …)` and idles the looper until the callback answers, and writes `Bitmap.compress(PNG)`. The system property `robolectric.pixelCopyRenderMode=hardware` is set, so `PixelCopy` goes through `HardwareRenderer` as Robolectric documents; a run without it wasn't compared.
   - **Not `onRoot().captureToImage()`.** In Compose UI 1.9 it first forces a redraw and waits for a frame-commit callback with `Thread.sleep` on the test's thread. Under Robolectric that thread is the main looper's, so the posted redraw never runs and every capture failed with "Condition still not satisfied after 2000 ms" (`WindowCapture.android.kt:178`). Calling `PixelCopy` directly does the same without the wait. Roborazzi was not needed: it would add only a capture call, and this one works.
   - **Paparazzi, compared once.** Paparazzi 1.3.5 failed before drawing anything on the fixture (`NoSuchElementException` in `Renderer.configureBuildProperties`: it doesn't know `compileSdk` 36). 2.0.0-alpha05.1 drew `HomeScreen` with real glyphs, Arabic shaped as well as Robolectric's. But the Arabic locale didn't mirror the layout (its `DeviceConfig` takes the layout direction separately), it saves pictures scaled down to 1000 px tall unless told otherwise, it draws a composable with no activity (no launcher, no navigation, no ATF on the same tree), and it is a Gradle plugin applied in the module's build file. An init script would have to put it on the build's classpath next to the Android plugin, which Robolectric doesn't need. Its speed was the same: 3.5 s for the first snapshot and about 0.1 s for each after it, against Robolectric's 2.4–2.8 s and 0.12 s. Robolectric stays the choice.
2. **The test and its libraries come in through a Gradle init script, and the developer's build files are never edited.** Motif writes `<module>/.motif/shot/src/dev/motif/shot/MotifShotTest.kt`, `<module>/.motif/shot/init.gradle` and `<module>/.motif/shot/config.json` (with `<module>/.motif/.gitignore` set to `*`), and deletes all three when the run ends, whatever the outcome. `result.json` stays, and is deleted before each run.
   - **Groovy, `init.gradle`, not `init.gradle.kts`.** The Android plugin isn't on an init script's own classpath. A Kotlin init script can't name its types (`ApplicationExtension`) and would need `withGroovyBuilder` for every call; Groovy reaches the `android` DSL as it is.
   - **Only the module it sits in.** The script finds that module from its own path (`initscript.sourceFile`, three folders up) and matches it against `project.projectDir`, so Motif passes no module name and a monorepo's other modules are untouched.
   - **What it does,** in `pluginManager.withPlugin("com.android.application")`:
     - in `androidComponents.finalizeDsl` (after the module's build file, before the Android plugin locks its DSL): `sourceSets.test.java.srcDir(.motif/shot/src)` (Kotlin sources included) and `testOptions.unitTests.includeAndroidResources = true`;
     - `testImplementation` of `androidx.compose.ui:ui-test-junit4` and `ui-test-manifest` with no version of their own, only `prefer "1.9.0"`, so they take the version the app's BOM requires. androidx also keeps a group's libraries aligned, so an app that pins `ui` without a BOM gets them at its `ui` version. On the fixture they resolved to 1.9.0 from BOM 2025.08.00. `ui-test-manifest` is there as the plan lists it; the harness doesn't need it, since its blank activity comes from `Robolectric.buildActivity`;
     - `org.robolectric:robolectric:4.17`, `junit:junit:4.13.2` and ATF `com.google.android.apps.common.testing.accessibility.framework:accessibility-test-framework:4.1.1`, pinned;
     - on the unit-test `Test` tasks: the system properties `motif.shot.config` (the absolute path of `config.json`), `robolectric.graphicsMode=NATIVE` and `robolectric.pixelCopyRenderMode=hardware`, and `outputs.upToDateWhen { false }` with `outputs.cacheIf { false }`. Without these, Gradle would call the task up to date when only the options changed, and draw nothing.
   - **It adds no repositories.** The libraries come from the project's own `google()` and `mavenCentral()`, which the template declares under `FAIL_ON_PROJECT_REPOS`.
   - **Robolectric's own download.** The first time, Robolectric itself downloads `android-all-instrumented` (200 MB for SDK 35) into `~/.m2/repository`, from `https://repo1.maven.org/maven2`. This happens in the test JVM, outside Gradle's repositories and proxy settings.
     - **Its settings** are the test JVM's system properties: `robolectric.dependency.repo.url` (and `.repo.id`, `.repo.username`, `.repo.password`) for a mirror, `robolectric.dependency.proxy.host` and `.proxy.port` for an HTTP proxy, and `robolectric.offline=true` with `robolectric.dependency.dir` for a folder of jars and no network (read in Robolectric 4.17's `MavenRoboSettings` and `LegacyDependencyResolver`). `maven.repo.local` moves the cache.
     - **What the init script passes on**, the smallest mapping that covers what a developer has usually already set for Gradle. First, every `robolectric.dependency.*` and `robolectric.offline` system property of the Gradle build, which is how `systemProp.robolectric.dependency.repo.url=…` in `gradle.properties` (the project's or `~/.gradle/`) reaches Robolectric. Then, when no Robolectric proxy is given, Gradle's own HTTPS proxy (`systemProp.https.proxyHost` and `https.proxyPort`, port 443 when not given) as Robolectric's proxy. Failing that, the `HTTPS_PROXY` (or `https_proxy`) environment variable, read as a URL (port 80 for `http://` when not given). Proxy credentials aren't passed on.
     - **Proven.** With the jar removed from `~/.m2`, the run failed through the mapping both ways: once with `systemProp.robolectric.dependency.repo.url=http://127.0.0.1:9/maven2` in the copy's `gradle.properties`, and once with `HTTPS_PROXY=http://127.0.0.1:9` in the environment (Gradle itself ignores that variable, and built from its cache). With the network open and no settings, the same download had worked (8). The configuration cache still stores and reuses the script's entry.
     - **What Gradle's plain console showed** in both runs:
       ```
       MotifShotTest > classMethod FAILED
           java.lang.AssertionError at MavenArtifactFetcher.java:130
               Caused by: java.util.concurrent.ExecutionException at AbstractFuture.java:168
                   Caused by: java.net.ConnectException at null:-2
       ...
       > There were failing tests. See the report at: file:///…/app/build/reports/tests/testDebugUnitTest/index.html
       ```
       The test report's message is `Failed to fetch maven artifact org.robolectric:android-all-instrumented:15-robolectric-13954326-i7`. `ROBOLECTRIC_DOWNLOAD_FAILED` in `harness.ts` matches both, and is tested against this output; `motif shot` turns it into the offline message (11). It took 22 s, the build included, so the failure is quick, not a hang.
   - **Proven** with the template's version catalogue and Kotlin build file (the fixture), with a Groovy `build.gradle` (a hand-converted copy), with `--configuration-cache` (the entry was stored, then reused, and the test still ran), and with `--warning-mode all` (no warnings from the script). On the floor toolchain too (see 9).
3. **The run starts the project's Gradle wrapper with `java`, not `gradlew.bat`.** From the project's root, Motif runs `java -Xmx64m -Xms64m $JAVA_OPTS $GRADLE_OPTS -Dorg.gradle.appname=gradlew -classpath gradle/wrapper/gradle-wrapper.jar org.gradle.wrapper.GradleWrapperMain :<module>:testDebugUnitTest --tests dev.motif.shot.MotifShotTest -I <module>/.motif/shot/init.gradle --console=plain`. Every path in it is relative to the root.
   - **Client JVM options.** `JAVA_OPTS` and `GRADLE_OPTS` are passed to the client JVM after gradlew's own `-Xmx64m -Xms64m`, as gradlew passes them. They are split at spaces, with `"…"` or `'…'` keeping a value with spaces in one piece (`splitJvmOptions`).
   - **Which JDK (`gradleJava` in `compose/doctor.ts`).** Skipping gradlew mustn't change the JDK Gradle runs on, since the client's JDK is the daemon's and the Android plugin's. Motif picks as gradlew does, JAVA_HOME first, but only a java that is 17 or newer:
     - first, `$JAVA_HOME/bin/java` when it runs and is 17 or newer;
     - then the first that is 17 or newer of the PATH's `java` and Android Studio's bundled JDK.
     - A JAVA_HOME that is older, or doesn't run, is passed over. gradlew would stop there instead, with "JAVA_HOME is set to an invalid directory", or fail later in the Android plugin.
     - With none 17 or newer, the run is refused in doctor's words ("JDK 11.0.2 is older than 17, which Android's build needs.", or "No JDK found. …"). `motif doctor` reports the same JDK.
   - **`JAVA_HOME` for the run** is that JDK's own `java.home`, read from `java -XshowSettings:properties -version`. A launcher such as `/usr/bin/java` or Oracle's `javapath` gives the real JDK folder, not its own parent. Without that line, the home is two folders up from the program with links followed.
   - **Why not `gradlew.bat`.** It breaks on a path with `&` in it. In `C:\tmp\motif spike & co\cm`, `cmd /c .\gradlew.bat …` printed `'co\cm\' is not recognized as an internal or external command` and `Unable to access jarfile C:\tmp\motif spike\gradle\wrapper\gradle-wrapper.jar`. The script sets `DIRNAME=%~dp0` unquoted, so cmd splits the line at the `&`. The same command through `java` drew both screenshots there. It is also the same on every operating system, and the `java` is the one `motif doctor` found.
   - **On Windows, `gradlew.bat` must also be named with `.\`.** With `NoDefaultCurrentDirectoryInExePath` set (it is in this environment), `cmd /c gradlew.bat` doesn't look in the current folder.
   - **The environment.** `JAVA_HOME` is set to the chosen JDK, and `ANDROID_HOME` to the SDK doctor found when it isn't set, so a project without `local.properties` still builds. `compose-render.test.ts` runs that way.
   - The project's `gradle.properties` (`org.gradle.jvmargs`, `org.gradle.java.home`) still applies to the daemon. A project with its own changes to `gradlew` (extra JVM options in the script) is run without them.
   - **Output.** Gradle's output is read as it arrives. After the client exits (or is stopped at the time limit), Motif waits at most 3 s more for the pipes to close, so a process left holding them can't keep the run waiting; what arrived is kept.
4. **Sizes, density, scheme and locale are Robolectric qualifiers**, set with `RuntimeEnvironment.setQualifiers` before each shot's activity starts, in Android's qualifier order: `<locale>-w<W>dp-h<H>dp-<port|land>-<night|notnight>-xhdpi` (for example `ar-w390dp-h844dp-port-night-xhdpi`).
   - **Sizes.** The four native sizes are Flutter's, at xhdpi (2×): `mobile-360` gives 720×1600, `mobile` 780×1688, `mobile-430` 860×1864, `tablet` (768×1024) 1536×2048. All were drawn and looked at.
   - **No system bars.** The picture is the whole window. Robolectric reports no status or navigation bar, so an edge-to-edge app's content starts at the top edge, and `Scaffold`'s insets are zero. Flutter's shots get an iPhone-like safe area. Task 9 gives Compose's the same: see 11.
   - **Night and locale.** `night` makes `isSystemInDarkTheme()` true. A locale such as `ar` picks `values-ar` and lays the screen out right to left (a `Row` mirrors; checked on Settings at every size).
   - **Remove animations** is `Settings.Global.ANIMATOR_DURATION_SCALE`, written before each shot: 0 with reduced motion, 1 without. The generated `MotifMotion.reduced()` read `true` and `false` accordingly, in the same run.
   - **Dynamic colour.** The template's theme uses dynamic colour from Android 12. Robolectric's Android 15 answers with the system's default palette, so the fixture is drawn in that blue, not the template's purple, as on a phone with the default wallpaper. An app on `MotifTheme` isn't affected.
5. **Fonts.**
   - **`res/font` fonts render**: Noto Naskh Arabic, used through `FontFamily(Font(R.font.noto_naskh_arabic))`.
   - **System fonts are there,** unlike Flutter's test font: Robolectric's Android jar has Android's own fonts. Text in `FontFamily.Default` is Roboto, and Arabic text whose font lacks Arabic falls back to the system's Noto Naskh Arabic, as on a phone. A missing companion therefore gives a different font, not boxes.
   - **Google fonts** don't download under Robolectric: there is no Google Play services font provider. Without help, `MotifFonts.onest` was drawn in Roboto, with no error. The harness sets `MotifFonts.debugFontOverride` through reflection (`<package>.MotifFonts.INSTANCE.setDebugFontOverride(Function1)`). The override answers each family by the guide's name with `FontFamily(Font(File, FontWeight, FontStyle), …)`, from the TTFs in Motif's font cache (`motifHome()/fonts/google/<Family>/`, downloaded once by `googleFontFiles`, as for Flutter). `composeFont` in `harness.ts` turns the cache's files into weights and styles.
   - **Checked by eye:** Onest (body) and Readex Pro (the Arabic companion, `MotifType.bodyArabic`) were drawn in their own shapes, beside a `FontFamily.Default` line in Roboto for comparison.
   - **The variant** is set the same way: `<package>.MotifTheme.INSTANCE.setDebugVariantOverride(<MotifVariant>)`. A `Partner` dark shot came out in the partner palette, unlike the default dark one.
6. **Screens: the launcher activity, routes through the app's own NavController, and previews in a blank activity.**
   - **`/`** is the launcher: `packageManager.getLaunchIntentForPackage(packageName)`, started with `ActivityScenario.launch`.
   - **Any other route** starts the launcher too, then tells the app's own `NavController` to open the route: `navigate(route, null, null)`, called through reflection so the harness compiles in an app without Navigation.
   - **Finding the NavController.** Compose records each composition's slot table in a set that Layout Inspector tags on the view (`androidx.compose.ui.R.id.inspection_slot_table_set`). The harness puts that tag on the activity's composition roots in `onActivityPostCreated`, before the first composition. After the launch it looks through the remembered values for a `NavController`. This works for any graph shape and any `NavHost` route, and leaves the back stack as a tap would (home, then settings).
   - **The deep link, tested and kept as the fallback** (implemented in Task 9, see 11). `KEY_DEEP_LINK_IDS` set to `[0, "android-app://androidx.navigation/settings".hashCode()]` also reached Settings. It needs every id from the root graph down: 0 for a `NavHost` without a route, its route's hash otherwise, and each nested graph's id. It also needs `FLAG_ACTIVITY_NEW_TASK` cleared from the launch intent, or Navigation restarts the task, finishes the activity and leaves a blank picture. An `android-app://…/<route>` URI in the intent's data doesn't match at all: Navigation keeps route deep links private and matches only explicit ones.
   - **Left open by the spike, settled in Task 9 (11):** type-safe routes, several `NavHost`s, and the start destination found as its own route (`/home` next to `/`).
   - **Previews:** `Robolectric.buildActivity(ComponentActivity::class.java).setup()`, then `setContent { … }` calling the function from `Class.forName("<package>.<File>Kt").getDeclaredComposableMethod(name)` (compose-runtime's `androidx.compose.runtime.reflect`). The method's `isAccessible` is set and it is called with `invoke(currentComposer, null)`. A compiled composable takes a `Composer` and a "changed" mask, which this supplies. A `private` preview (`SettingsPreview`) worked, and so did the names `discoverComposeScreens` gives (`dev.motif.composemin.ui.screens.HomeScreenKt.HomePreview`).
   - **Waiting.** `compose.waitForIdle()` returned with an indeterminate `CircularProgressIndicator` on screen, and the next shot was fine. The bounded 5 s wait the plan describes is Task 9's (11).
7. **One test method drew every shot in the spike,** so Robolectric's sandbox starts once. Task 9 changed this to one test per screen (11). Each shot's error is caught and recorded, and the run goes on. The harness writes `result.json` in the shape of Flutter's (`screens: [{ route, shots, errors }]`, `shots: [{ file, error? }]`, `issues: []`, `notes: []`), plus `timings: [{ file, ms }]`. Global state carries over between shots in a run: the font override, the app's singletons and its `object`s. The variant and Remove animations are set again for every shot.
8. **Timings, and the run's time limit.** Measured on the fixture (Windows 11, Android Studio's JBR 21.0.5, Gradle 8.14.3, AGP 8.13.1):

   | Run | Time |
   |---|---|
   | First run on a machine: empty Gradle user home and no Robolectric jars (Gradle, the Android plugin, Compose and 200 MB of Android downloaded, 1.3 GB in the Gradle home), 2 shots | 213 s |
   | First run in a fresh copy, caches full, no Gradle daemon running, 2 shots | 30.3 s |
   | Fresh copy, daemon running (the build itself from nothing), 2 shots | 9.4 s |
   | Later runs, 2 shots | 9.1 s |
   | Later runs, 10 shots | 9.9 s |
   | Later runs, 40 shots | 13.4 s |
   | Later runs, 80 shots (5 screens × 4 sizes × light/dark × LTR/RTL) | 18.1 s |
   | The floor toolchain (JDK 17, AGP 8.6.1, Gradle 8.7, Kotlin 2.0.0), its Gradle downloads included, 2 shots | 85 s |

   - Inside a run, the first shot takes 2.4–2.8 s (Robolectric's sandbox and the app's first composition). Each later shot takes about 0.12 s (at most 0.28 s of the 80).
   - **The time limit Task 9 uses is 600 s plus 5 s per screenshot.** This is a judgement, not a measurement. The measured basis is 213 s for a machine's first run, on a fast connection, for a small app. The 600 s allows for a slower connection (about 1.5 GB comes down) and a slower CI runner. The 5 s is the plan's bounded wait per shot, about 40 times the measured 0.12 s, so a run whose every screen waits to its cap still finishes.
   - When the limit is reached, the runner stops the Gradle client's process tree. Gradle then cancels the build and its test JVM. A daemon started by an earlier run stays for the next one.
9. **Floors.** The fixture's own versions are at three of them: Compose UI 1.9.0 and Material 3 1.3.2 (BOM 2025.08.00), and Kotlin 2.2.20. A copy at the other floors ran the harness and drew both screenshots: Kotlin 2.0.0 (with its Compose compiler plugin), `compileSdk` and `targetSdk` 35, Temurin JDK 17.0.20.1 for both Gradle and the test, AGP 8.6.1 and Gradle 8.7.
   - **Kotlin 2.0, Compose UI 1.9, Material 3 1.3, JDK 17 and `compileSdk` 35 are confirmed.**
   - **The Android Gradle Plugin floor is raised from 8.5 to 8.6.** With AGP 8.5.2, `checkDebugAarMetadata` refused the build: "Dependency 'androidx.compose.ui:ui-android:1.9.0' requires Android Gradle plugin 8.6.0 or higher". `ui-text-google-fonts` 1.9.0, `runtime-saveable` 1.9.0, `core` 1.16.0 and lifecycle 2.9.2 said the same. Compose UI 1.9 can't be used below AGP 8.6, so 8.6 is the floor, with Gradle 8.7 (AGP 8.6's minimum). `doctor` doesn't check the plugin's version; the guide (Task 11) must say 8.6.
10. **CI on Linux** gets its own `compose` job in `ci.yml`. It runs on `ubuntu-latest` with `actions/setup-java@b843ebf9b913146b38da2eaa7aeddf76074ae1ad` (v6.1.0, Temurin 17) and `android-actions/setup-android@be39fa834029ff78f1a44aa3bb0819b8fc2bd8fd` (v4.0.4, `platforms;android-36`), and runs `compose-compile.test.ts` and `compose-render.test.ts`. Both actions are pinned to a commit, like the others. Robolectric's native graphics ship for Linux, macOS and Windows, but this hasn't been run on Linux yet; the job's first run will prove it. GitHub's hosted runners already have a JDK and an Android SDK, so the main matrix's test job may run these tests too: `hasAndroid` is true there.

11. **What `motif shot` does with the harness (Task 9).** `cli/src/stacks/compose/shot.ts` is `COMPOSE.shoot`, in Flutter's five steps. `cli/test/shot-compose.test.ts` (a stand-in for Gradle) and `cli/test/compose-shot-e2e.test.ts` (real Gradle, on a copy of `compose-min` in a path with a space and an `&`) test it.
   - **One test per screen.** The harness is a `ParameterizedRobolectricTestRunner` test with one parameter per screen, read from `targets.txt` next to `config.json`. The `@Parameters` method runs outside Robolectric's sandbox, where Android's `org.json` isn't, so it reads a plain list. Each screen adds itself to `result.json`.
     - The reason: a composition that throws (a screen whose ViewModel calls the network, say) takes the test rule's one Recomposer down with it. Every later shot in the same test then drew its first composition only, with no navigation, insets or recomposition, and no error.
     - Proven: with one test, `/crash` threw and the `/settings` shots after it showed Home; with a test per screen, `/settings` was right.
     - The cost is one more Robolectric environment per screen: a default run of 6 screens and 41 shots took 19 s in all, Gradle included.
   - **A screen stops at its first failure;** its other shots are recorded with the same error, since they'd fail the same way.
     - A composition's exception is held by the test rule until a wait for idle ends, and a wait that timed out never gets there. So after each shot the harness calls the rule's own `throwPendingException` and `UncaughtExceptionHandler.throwUncaught` by reflection (the environment is an anonymous subclass: they're its superclass's).
     - The shot's PNG, which shows the screen before the failure, is deleted.
     - The error reads "/ couldn't start in a test: IllegalStateException: …. Draw its screens from previews (--screen), or set it up in design/states/Setup.kt."
   - **An `Application` that can't start.** Robolectric creates the app's `Application` before the test, so its exception fails the test before the harness runs.
     - Each screen therefore has two tests, in name order: `a_shots` with the app's own `Application`, then `b_plainApplication` with `@Config(application = Application::class)`, which draws the screen only when `a_shots` added nothing for it.
     - The run's note gives the reason from Gradle's JUnit report (`TEST-dev.motif.shot.MotifShotTest.xml`, the first `a_shots[…]`'s failure message). It says previews draw as they are, while screens that need what it sets up may not start.
     - Proven with an `Application` whose `onCreate` throws: the previews and `/` were drawn.
   - **Settling, bounded.** Under Robolectric, `compose.waitForIdle()` loops until idle for as long as Espresso's master idling policy allows (`RobolectricIdlingStrategy` reads it).
     - The harness sets it to 5 s (`settleMs`) by reflection, since Espresso is only on the test's runtime classpath, and to 15 s while a state runs.
     - A screen that doesn't settle is drawn as it is, with a note.
   - **System bars.** A phone's shots (width under 600) get a status bar of 47 dp and a navigation bar of 34 dp, as Flutter's do.
     - The harness dispatches `WindowInsetsCompat` with those `statusBars` and `navigationBars` insets to the decor view after the activity settles, then settles again.
     - Checked by eye: an edge-to-edge `Scaffold`'s content starts 94 px lower at xhdpi.
     - Previews get none: they're drawn as Android Studio shows them, without system UI.
   - **Routes.** `/` is the launcher as it starts. Another route is opened by the app's own NavController.
     - With several `NavHost`s, it is the outermost whose graph has the route (`NavGraph` walked by reflection), else the outermost.
     - When the controller already shows the route (the start destination), nothing is pushed. Discovery drops the start destination of an app's only `NavHost`, since it is `/`. With several, each one's start stays a route.
     - After `navigate`, the current destination must be the route, or the error says where it stayed.
     - A type-safe route (`@Profile`) is matched by its destination's route (the class's serial name). It is opened with an instance of the class (its `object`, or the constructor Kotlin generates when every parameter has a default), else by that name as a string. Type-safe routes weren't tried end to end.
   - **The deep link, implemented.** It is used when there is no NavController in the composition, or with `deepLinks` in the options, which the end-to-end test uses to prove it.
     - The launcher's own first screen is drawn, the activity is started again with `KEY_DEEP_LINK_IDS = [0, hash]` and without `NEW_TASK`/`CLEAR_TASK`, and the two pictures are compared.
     - The same picture means the link didn't land: "…a deep link to /nowhere showed the first screen instead. Draw it from a preview (--screen)."
     - It reaches only a destination of a root graph without a route of its own; a type-safe route has no deep link.
   - **Right to left** is the `ldrtl` qualifier after the locale (`he-ldrtl-w390dp-…`), so the shots are mirrored even in a language the app has no strings for. Without a `res/values-<lang>` folder (`values-iw` counts for Hebrew), the note says the app doesn't offer it, and that the shots show its default strings, laid out right to left.
   - **The variant** is set on every shot, the default's included. So an app that calls `MotifTheme(variant = MotifVariant.Partner)` itself is drawn in the guide's default for the default's shots. Proven: its default and partner shots differ, and the partner shot's background is the partner's.
   - **Setup and states.** `design/states/Setup.kt` (package `dev.motif.states`, `motifSetup(variant, locale, dark)`) and each `--state` file (package `dev.motif.states.<name>`, `motifState(rule: ComposeContentTestRule)`) are copied into the test source folder, with a generated `MotifHooks.kt` that calls them.
     - The harness finds `MotifHooks` by reflection, so `compose-render` still runs it without one.
     - The setup runs before each shot's activity starts. Proven: a setup that sets a signed-in flag in `SharedPreferences` reached the signed-in screen.
     - `createEmptyComposeRule()` returns an `AndroidComposeTestRule`, which is a `ComposeContentTestRule`, so states get that type. Task 10 tests states end to end.
   - **Before the run.** No JDK 17 or no SDK is refused with `needs-android` and doctor's words; no `gradle/wrapper/gradle-wrapper.jar` with `needs-gradle-wrapper`. When `~/.m2/repository/org/robolectric/android-all-instrumented` doesn't exist, the run says that it downloads Robolectric's Android libraries, before it starts (on the progress line) and in its notes. A different `maven.repo.local` isn't followed, so the note may then appear on a run that doesn't download.
   - **Gradle failing.** With no `result.json`, an output that matches `ROBOLECTRIC_DOWNLOAD_FAILED`, "Could not resolve" or `UnknownHostException` gives "Gradle couldn't download what the screenshots need. Connect to the internet for the first run; later runs work offline." Any other failure gives its last 20 lines.
   - **A module elsewhere.** The Gradle path comes from the settings file when it maps one to the module's folder (`project(":app").projectDir = file("android/app")`, or `new File(settingsDir, …)` in Groovy); `init.gradle` already matches the module by its folder. Detection (Task 1) still lists modules by their include path's folder, so such a module is screenshotted only when it's found as an app some other way.

## Consequences

- Motif can draw a Compose app's screens with only a JDK and the Android SDK: no emulator, and no change to the app's build. This was proven on Windows with one small app. Task 9 met apps whose `Application` or screens can't start in a test (11); Hilt, and an app with its own Robolectric version, weren't tried.
- The first run on a machine downloads about 1.5 GB (Gradle, the Android plugin, the libraries, Robolectric's Android) and takes minutes. Robolectric's own download ignores Gradle's repositories, so the init script passes on a mirror or proxy the developer set for Gradle (2). Later runs work offline from the caches.
- The app's own unit tests are compiled in the same task (`testDebugUnitTest`) but not run (`--tests`). If they don't compile, the screenshots fail with them.
- The harness relies on two things that aren't public API: Layout Inspector's slot-table tag, to find the NavController, and Robolectric's `PixelCopy`. If a later Compose drops the tag, the deep link (6) is the way left for routes. If Robolectric's `PixelCopy` stops working, the way left is `View.draw` on a software canvas, which wasn't tried.
- The same app can give PNGs that differ slightly between operating systems (font hinting). Motif's tests compare sizes and whether light differs from dark, not exact pixels.
- `MotifFonts.debugFontOverride` and `MotifTheme.debugVariantOverride` are what make Google fonts and variants work. An app that doesn't use the generated theme draws Google fonts in Roboto, and the run says so in a note.
