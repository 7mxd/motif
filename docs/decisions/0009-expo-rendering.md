# 0009 — Rendering Expo screens

- Date: 2026-10-20
- Status: Accepted
- Context: `motif shot` on an Expo app (plan 2G) starts the app's web target and captures it with the browser pipeline that web apps use (`captureScreens`), at the native sizes of decision 0007. The question for this spike (plan 2G, Task 7) was whether those pictures can be trusted for what Motif judges: the guide's colours in light and dark, its design variants, its fonts (Google and the project's own), and Arabic right to left. It also had to find what the web target can't show, and how an app that can't run on the web fails. The spike ran on Windows 11 with Node 22.14.0, npm 11.13.0, Bun 1.4.3 and Chrome 155, on `cli/test/fixtures/expo-min` (Expo SDK 58.0.16, React Native 0.88.0, react-native-web 0.21.4, React 19.3.0, Reanimated 4.7.1, expo-router 58.0.24, Metro 0.87.1, TypeScript 6.0.3), and once on an SDK 52 copy of it (see 8). For the spike the fixture grew: a guide (`design/tokens.json`) with a `partner` variant, Onest from `@expo-google-fonts/onest` with Noto Naskh Arabic (the project's own `.ttf`) as its companion, the generated `design/motif-theme.tsx`, an English and Arabic string table chosen by the locale (`i18n/strings.ts`), `I18nManager.forceRTL` called only on native, and a root layout that passes its own variant (`variant="partner"`) to `MotifProvider`. `cli/test/rn-shot-e2e.test.ts` runs it end to end.

## Decisions

1. **Expo apps are drawn by their web target in Chrome, and the pictures are the app.** Every look the spike tried came out right, checked by eye in the PNGs and from inside the page (the e2e test's state script reads each screenshot's background colour, its title's font and whether that font loaded, and the direction):
   - **Dark mode.** react-native-web's `useColorScheme()` follows the emulated `prefers-color-scheme`, so `MotifProvider` picks the guide's dark colours. Light and dark PNGs differ.
   - **Variants.** The provider's `MutationObserver` on `data-variant` switches the colours after the page has loaded; Motif sets the attribute after load, as for web apps. `index+partner.mobile.png` shows the partner's background and button.
   - **Fonts.** `expo-font` on the web adds an `@font-face` rule per key of `motifFonts` (`Onest_700Bold`, `"Noto Naskh Arabic_400"`), and the app renders nothing until `useFonts` says they're loaded. `document.fonts.ready`, which capture already awaits, then covers them: every face the screen uses has the status `loaded` before the screenshot. Google fonts come from the package's files in `node_modules`, so no network is needed.
   - **Arabic.** Motif's `--rtl ar` sets the browser's language and Intl locale, so the app's own table gives Arabic strings and the provider's `readsRtl()` sees an Arabic locale (`Intl`) and uses `typeArabic`: the text is drawn in Noto Naskh Arabic, the companion font. See 4 for the direction.
2. **The default's screenshots name the default variant too.** An app that passes its own variant to `MotifProvider` (as expo-min does) was drawn in that variant in the default's screenshots, and Motif then noted that the partner variant "looks exactly like the default" (the 2E lesson again). When the guide has variants that validate, every browser stack's default screenshots now set `data-variant` to the default's id (`captureScreens`' `defaultVariant`). The provider prefers the attribute on the web, so the default is drawn in the default. Motif's web CSS has no rule for the default's id (`:root[data-variant="<id>"]` exists only for the other variants), so React web and plain web pages look the same; `capture.test.ts` pins both, in the generated files and in the browser.
3. **The app's own fixed light or dark is followed.** `userInterfaceStyle` in `app.json` isn't applied on the web: with `"light"`, the web target still turned dark when the browser asked for dark, so the `.dark` screenshots showed a dark mode the phone never draws. Expo's default when `app.json` doesn't set it is `"light"` (its config types say so). Motif now reads `app.json` (`fixedScheme`): `ios.userInterfaceStyle` and `android.userInterfaceStyle`, each falling back to the top-level value and then to `"light"`. When the two agree on `light` or `dark`, every screenshot is taken in that scheme (`captureScreens`' `appScheme`), and the run says why, for example: "app.json sets userInterfaceStyle to "light", so on a phone the app stays light in dark mode: its .dark screenshots are drawn light too. Set it to "automatic" to follow the phone's setting." The `.dark` files are still written, so names and comparisons with mockups stay the same. With `"automatic"`, an `app.config.*` (which can change the value, and which Motif doesn't run) or no `app.json`, the browser's setting is followed. On Android, Expo applies the setting only when `expo-system-ui` is installed; Motif doesn't check for it. An app that follows the setting but draws dark exactly like light (it never reads `useColorScheme`, as expo-min didn't before the spike) gets "Dark mode looks exactly like light on every screen: …". Only screens that drew without an error count, since a crashed screen looks the same in both.
4. **`--rtl` turns the page right to left; the app's `I18nManager` doesn't.** react-native-web's `I18nManager.isRTL` is always false, `forceRTL` does nothing there, and Expo's HTML template has `<html lang="en">` with no `dir`. Text views get `dir="auto"`, so each Arabic line runs right to left, but the layout doesn't mirror. Motif's existing rule for web pages covers this: the page isn't `rtl` after load, so Motif sets `dir="rtl"` and `lang` on `<html>` and notes "/ doesn't switch to right to left by itself for ar; Motif set dir="rtl" to show it." Flex rows then mirror, as they would on a phone with `forceRTL`. The provider reads the direction when it renders and isn't told when `dir` changes. That doesn't matter here, because the Intl locale is already Arabic when it first renders. An app that chooses Arabic from something other than the locale (a stored setting) would need a state script to set it.
5. **Expo builds the web bundle before the first screenshot, and a bundle it can't build stops the run.** In the spike, a route that imports a package that isn't installed made Metro answer the page's one script (`/node_modules/expo-router/entry.bundle?platform=web&dev=true&…`) with HTTP 500 and JSON (`{"type":"UnableToResolveError","targetModuleName":"some-missing-package","originModulePath":"C:\\…\\app\\missing.tsx","message":"Unable to resolve module some-missing-package from …"}`). The page answered 200 and threw nothing, so every screenshot was blank and the run said nothing was wrong. Expo printed "Web Bundling failed … Unable to resolve "some-missing-package" from "app\missing.tsx"" in its own output, which Motif doesn't show once the server has started. Now, once the server answers, Motif fetches the page and its scripts (`buildWebBundle`) before any screenshot:
   - A script that fails stops the run (`web-bundle-failed`, exit code 1) with Metro's reason in the app's own paths: "Expo couldn't build the app for the web, so there's nothing to screenshot: app/missing.tsx imports some-missing-package, which isn't installed. Install it (npx expo install some-missing-package) or remove the import." For an import from inside a package, Motif suggests `npx expo install --fix` instead. For a package that is installed but has no web version, it says how to keep it out of the web (6).
   - SDK 52's Metro sends the same JSON without `type`, so the module and origin fields are read on their own.
   - Any other error gives its first line, without colour codes.
   - This also moves Metro's first bundle into the start limit (7). Before, it fell to the first page's 60 s load wait, and a big app's cold bundle could have run past it.
6. **What native-only code does on the web, and the hints.** A Metro build doesn't fail for native-only code that exists on disk: the app starts and then throws. The spike saw two shapes:
   - `react-native-maps` (its specs call `codegenNativeComponent`) throws `TypeError: (0 , _reactNativeWebDistIndex.codegenNativeComponent) is not a function` while the bundle loads. The message names no package. Expo's `"single"` web output puts every route in one bundle, so this stopped **every** route, `/` included, not only the one that imports the map. Expo's error overlay (LogBox, drawn in a shadow root) covers the screenshot and names the file (`node_modules/react-native-maps/src/specs/NativeComponentGooglePolygon.ts`).
   - `expo-secure-store` throws `TypeError: ExpoSecureStore.default.getValueWithKeySync is not a function` when the screen renders, on that route only.
   - The hints Task 6 wrote matched shapes the spike never saw. "Unable to resolve module …" arrives only in Metro's HTTP answer (now 5), never as a page error. "Cannot find module '…'" and "… in react-native-mmkv" didn't occur. Their advice (a `<package>.web.tsx` beside the import) doesn't work, because a platform extension applies to the app's own files, not to a package. The hints (`webErrorHints`) now match what was seen: `_reactNativeWebDistIndex.<name>` (a React Native API that react-native-web lacks), `Expo<Name>.default.<fn> is not a function`, and Expo's own `Cannot find native module '<Name>'`. An Expo module is named by its package when the app lists it (`ExpoSecureStore` → `expo-secure-store`). The advice is to move the code into a file of its own with a `.web.tsx` twin that leaves it out. `shot-rn.test.ts` holds the exact texts.
   - A screen that threw as it loaded shows Expo's overlay, and auditing it judged the overlay ("Some text is hard to read" about the red sheet). Such Expo screens are left out of the audit with "✗ Audit incomplete: /secure threw an error as it loaded, so it isn't audited (its screenshots may show Expo's error overlay)." Then a run with nothing found elsewhere doesn't claim a clean audit.
7. **Timings, and the run's time limits.** Measured on expo-min (Windows 11, SDK 58, 2 routes, 1136 modules). "Cold" means an empty Metro cache, made by pointing `TEMP` at a new folder (Metro keeps `metro-cache` there, shared by every app on the machine):

   | Run | Time |
   |---|---|
   | Expo's server answers (`expo start --web`, `CI=1`) | 3.0 s |
   | First web bundle, cold cache | 2.7–2.9 s |
   | First web bundle, warm cache | 0.6 s |
   | `motif shot --sizes 390 --routes /` (2 screenshots), whole command, cold cache | 9.4–9.5 s |
   | The same, warm cache | 8.3 s |
   | 16 screenshots (2 routes, 390, 2 variants, `--rtl`) | 24–25 s |
   | 64 screenshots (2 routes, the four native sizes, 2 variants, `--rtl`) | 81 s |
   | `npm ci --prefer-offline` of the fixture, npm cache warm | 15 s |

   - The first screenshot comes about 9.5 s after the command starts: 3 s for the server, about 3 s for a cold first bundle, and the rest for the browser and the page.
   - Each extra screenshot costs about 1.2 s. Each one opens a new tab that loads the whole development bundle (several MB) again, waits for fonts and quiet, and settles for 400 ms. That is about 15 times the cost of a Flutter screenshot (60–75 ms, decision 0007), so an Expo run of 64 screenshots takes over a minute.
   - One cold run of the whole command took 32 s while the machine was busy; two repeats took 9.5 s.
   - The time limits are those of the web path plus Expo's start limit: **300 s** (`RN_START_TIMEOUT_MS`) for the server to answer *and* its first bundle to be built (5), then the browser pipeline's own limits (60 s for each page to load, 15 s for a state script). No limit covers the whole run, as there is none for web apps. The 300 s is a judgement, not a measurement: it is about 50 times the fixture's server and cold bundle (6 s), to allow for a real app with thousands of modules, a cold cache and a slower CI runner. No real app was timed.
8. **The floors hold on SDK 52.** A copy of expo-min with Expo 52.0.49, React Native 0.76.9, react-native-web 0.19.13, React 18.3.1, Reanimated 3.16.7, expo-router 4.0.22 and TypeScript 5.3.3 was set up by hand. Its generated theme passed `tsc --noEmit`, and `motif shot --sizes 390 --variant all --rtl` with the e2e test's check script drew all 32 screenshots (16 looks, each with the check's state) without an error, in 46 s, with the partner colours, the fonts and Arabic as on SDK 58. A hand-made SDK 52 `package.json` needed two packages that a `create-expo-app` project has. Without `expo-asset`, `expo start` stopped with "Error: The required package `expo-asset` cannot be found", which Motif showed through its existing start-failure message. Without `query-string` (expo-router 4.0.22 imports it, and the current `@react-navigation` 7 no longer brings it in), Motif's new bundle check (5) stopped with "node_modules/expo-router/build/fork/getPathFromState.js imports query-string, which isn't installed. …". The floors in `doctor` and the guide (SDK 52, React Native 0.76, TypeScript 5, Reanimated 3.16) stay as they are.
9. **Expo's `"static"` web output: every route is warmed, and every screen is waited for until it has drawn.** `create-expo-app`'s template sets `"web": { "output": "static" }`; expo-min pins `"single"`. The final review of plan 2G ran `motif shot --sizes 390 --routes /,/settings --variant all --rtl` on a copy of expo-min switched to `"static"` and got, 1 run in 3, a first screenshot showing only Expo's "Bundling… app/index.tsx" toast on a grey page, reported as a success. Reproduced here (SDK 58, cold Metro cache: `TEMP` pointed at a new folder each run): 2 of 3 runs had one such screenshot (`index.mobile.png`, the run's first: once react-navigation's grey card with the toast, once a white page); warm-cache runs were clean (3 of 3). Why: with `"static"`, Expo renders each page in Node, and the page's one script (`entry.bundle?…&lazy=true&transform.asyncRoutes=true`) loads each route (and the root layout) as a chunk of its own after the page, `/app/index.bundle?…&modulesOnly=true&runModule=false`, which Metro builds the first time it is asked. `buildWebBundle` fetched only the page's `<script src>`, so the chunk wasn't built, and while the browser waited for it expo-router's `SuspenseFallback` drew the toast; capture's quiet wait (300 ms without a request, at most 5 s) could pass during it. The rule now:
   - **Warm every route.** Before the first screenshot, `buildWebBundle` fetches each captured route's page (rendering it in Node with `"static"`), the scripts those pages load, and every web chunk the scripts name (Metro writes each lazily loaded chunk's address into the entry bundle as a JS string; a Windows path keeps its escaped backslash), four at a time, each once. A chunk Metro can't build stops the run with its reason, as the entry bundle does (5). All of it counts against the start limit (7).
   - **Wait until the screen has drawn.** For an Expo app (`captureScreens`' `reactNative`), after the page has loaded and gone quiet, each screenshot waits (polling every 100 ms) until Expo's "Bundling..." toast, or its fast-refresh badge, is gone and something in `#root` draws: text, an image, a field, or a background that isn't transparent (a layout waiting for `useFonts` returns `null`, so the root holds only Expo's transparent wrappers). If it had to wait, it waits for quiet and fonts again. A screen that threw isn't waited for: it is captured with its error, as before (6). One that hasn't drawn after 30 s is the route's error and isn't captured: "Expo was still bundling this screen 30 s after it loaded (its "Bundling..." toast was showing), so it wasn't captured. Run motif shot again; …", or "The screen was still empty 30 s after it loaded, so it wasn't captured. Open the page in a browser to see what it waits for (fonts loaded with useFonts, data it fetches) before it draws." Web and Flutter runs are unchanged.
   - **Result.** With both, 22 cold runs of the same command (some while other test suites ran on the machine) drew all 16 screenshots with the app's background and text (checked in the PNGs' pixels), none a toast or an empty page. One more ended before any screenshot, and its message wasn't kept (the timing script didn't print it); it didn't happen again; in 3 of them, logged, the wait was needed once (a `/settings` screenshot, after warming), so warming alone isn't enough. `rn-shot-e2e.test.ts` runs a copy of expo-min with `"static"` on a cold Metro cache (32 screenshots with the check script; every PNG's background and content are checked): it passed 5 runs in 5 with the fix and failed 2 in 3 without it. The toast's text ("Bundling...") is expo-router's (SDK 52's expo-router 4 has the same); a screen whose own text is exactly "Bundling..." would be waited for and then reported.
   - With `"static"` the HTML is server-rendered: it holds the screen as Node drew it (in the variant the app passes, since there is no `data-variant` in Node), so a check of the HTML alone would pass too early; the wait reads the live page. `"server"` output wasn't tried.

## Consequences

- Motif can screenshot an Expo app with only Node, its `node_modules` and a browser: no simulator, no emulator, no Mac. The colours, the fonts the app loads, dark mode, variants and Arabic are the app's own. What the web target can't show:
  - Native-only components: maps, camera previews, native date pickers. They throw rather than render.
  - Platform fonts: an app without loaded fonts is drawn in the browser's system font (Segoe UI on Windows), not San Francisco or Roboto.
  - Native navigation chrome: on the web, Expo Router's stack draws react-navigation's JS header, not UIKit's large titles or blur. The fixture hides its header, and the first spike run showed the default header ("index") in the browser's font.
  - What the phone's OS adds, such as the status bar and the safe-area insets around a notch. Chrome's device emulation has no notch, so the insets are presumably 0; the fixture doesn't use them, so this wasn't checked.
  - `I18nManager` (4) and `userInterfaceStyle` (3) are covered by Motif.
  - The first run's note says the screenshots are of the web target.
- One native-only import in any route stops every route on the web (6), and Motif can't name the package from the error, only point at Expo's overlay in the screenshot. Naming it would mean symbolicating the error's stack with Metro (`/symbolicate`), which wasn't built.
- `fixedScheme` reads `app.json` only. An app configured in `app.config.js`/`.ts` follows the browser's setting, and a light-only one can get dark screenshots its phones never show (it may get the "looks exactly like light" note if it doesn't read the scheme).
- Expo's `"single"` and `"static"` web outputs were tried (9); `"server"` wasn't. With `"static"` (and `"server"`), Expo renders pages in Node first: a native module may fail on the server instead, and the provider's first render has no `document` (a hydration mismatch is possible; Task 2's review noted it). On expo-min, the screenshots after hydration had the right variant, colours, fonts and direction (the check script passed in all of them).
- The audit and `--state` scripts work on the web target unchanged (plan 2G, Task 8; `rn-shot-e2e.test.ts` plants the problems in `test/fixtures/expo-audit-routes`). Found: a `#c8c8c8` caption on white (contrast, 1.67:1); a 32 px `Pressable` with `accessibilityRole="button"` and no label (react-native-web draws a `<button>`; axe passes it when its content is an Ionicons glyph, which is text to axe, and Motif's own name check reports it as kind "icon", with the 44 px target check reporting its size); a 32 px labelled one (size only); and a `withRepeat(withTiming(…), -1)` loop with `ReduceMotion.Never` (reduced-motion check, which samples computed transforms and sees Reanimated's per-frame styles). A state script fills a `TextInput` found by `aria-label` or `placeholder` (set the native value, dispatch `input`) and gives `form@filled.mobile.png`.
- What the audit does for Expo's controls (Task 8's review). react-native-web draws `Pressable`, `TouchableOpacity` and `TouchableHighlight` alike as `<div tabindex="0">` with a pointer cursor and no role, unless the app sets `accessibilityRole`/`role` (then a `<button>` or similar); `accessibilityLabel` becomes `aria-label`. axe and the 44 px query only know roles, so for Expo apps only (`captureScreens`' `reactNative`, set by `motif shot` for Expo; web and Flutter runs are unchanged, pinned in `audit.test.ts` and `shot-command.test.ts`) Motif also takes every `[tabindex]:not([role])` element that isn't an `a`, `button` or field, has a pointer cursor and isn't inside another control. They go through the 44 px check (light, phone) and a name check of Motif's own: no `aria-label`, `title`, `aria-labelledby` or readable text means "The button has no name". Text that is only private-use characters (U+E000 to U+F8FF, U+F0000 and above, where icon fonts such as `@expo/vector-icons` keep their glyphs) or `aria-hidden` doesn't count as a name. axe passes a `role="button"` whose only content is an Ionicons glyph (it is text to axe), so Motif's check also catches those, as kind "icon" ("The icon has no name"). The fixture's `Pressable`, `TouchableOpacity` and `TouchableHighlight` with an Ionicons glyph and no label all show as buttons with no name. Fix texts are React Native's own (`RN_FIXES`: `accessibilityLabel`, `hitSlop`, `useReducedMotion()`).
- Limits the audit has on Expo apps. (1) A control Motif can't tell from the markup: a `div` made tappable only by a touch handler that react-native-web doesn't give a `tabindex` (for example a `View` with `onStartShouldSetResponder`) is not seen. (2) Reanimated's animations stop by themselves under reduced motion unless the app passes `ReduceMotion.Never` (its default is `ReduceMotion.System`), so a loop without that setting is correctly not reported. Core `Animated.loop`, which doesn't check the setting, is found (the fixture's `/loop`); one that checks `useReducedMotion()` or `AccessibilityInfo` is not (`/calm`).
- Metro's cache is shared by every app on the machine (`%TEMP%\metro-cache` on Windows), so only an app's first run, or one after the cache is cleared, pays for the cold bundle.
- The audit judges the web target. A tap target on the web is the element's box: the fixture's 43.6 px "Settings" link is reported as "95×44 px … 44×44 px is easier to tap", since the size is rounded.
