# 0007 — Rendering Flutter screens

- Date: 2026-10-20
- Status: Accepted
- Context: `motif shot` must show a Flutter app's screens the way people see them, in every size, light and dark, and right to left, on any developer's machine and in CI. A device or simulator is slow, and an iPhone simulator needs a Mac. `flutter test` can draw an app with no device, but by default it draws text in a test font of solid boxes, and Motif has to judge type and contrast from these pictures. This spike (plan 2E, Task 8) checked on Windows 11 with Flutter 3.44.8 / Dart 3.12.2 whether `flutter test` can render `cli/test/fixtures/flutter-min` with its real fonts: Onest from google_fonts for Latin text, a bundled Noto Naskh Arabic for Arabic, and Roboto for plain Material text. It can. The harness skeleton is `cli/src/stacks/flutter/harness/motif_shot_test.dart`, and its runner is `cli/src/stacks/flutter/harness.ts`. `cli/test/flutter-render.test.ts` checks the `mobile` size in light and dark automatically. The other sizes and the right-to-left screens were rendered once by hand during the spike and checked by eye; Task 9's end-to-end test covers them.

## Decisions

1. **Screens are drawn by `flutter test`, from a test file inside the app's `.motif` folder.** Motif writes `<app>/.motif/shot/motif_shot_test.dart` and `<app>/.motif/shot/config.json` (with `<app>/.motif/.gitignore` set to `*`). From the app folder it runs `flutter test .motif/shot/motif_shot_test.dart --dart-define=MOTIF_SHOT_CONFIG=<config path>`, and it deletes both files when the run ends, whatever the outcome. `package:<app>/main.dart` imports resolve from there, and paths with spaces work, so the fallback (a `test/.motif_shot_test.dart`) isn't needed.
   - The harness source (`motif_shot_test.dart`) is the same in every run. What depends on the app is in a small `motif_hooks.dart` next to it (also deleted after the run): the import of the app's main file, and of `go_router`, `google_fonts` and `shared_preferences` only when the app depends on them; the generated `motif_theme.dart` when it has variants; `design/states/setup.dart` when it exists; and the `--screen` widgets' files. Everything else that varies (shots, fonts, HTTP fixtures, output folder) goes in the JSON file. Because of this, `flutter test` reuses its compiled test between runs of the same app (see 6). The harness writes `.motif/shot/result.json`, which the runner clears before each run and reads with a guard: a file cut short is a plain error with Flutter's last lines.
   - `flutter test` refuses to run an app that doesn't list `flutter_test` in `dev_dependencies` ("cannot run without a dependency on either package:flutter_test or package:test"). `flutter create` adds it, so most apps have it. Motif never edits `pubspec.yaml`: it checks first, stops (`needs-flutter-test`), and shows the three lines to add.
   - Navigation (Task 9): with go_router, the router is found from the app's `Navigator` elements (`GoRouter.maybeOf`), not a `Scaffold`, and every shot calls `go(route)`; a location go_router has no page for is reported as unreachable rather than captured as its error page. Without go_router, `/` is the app's home as started and other routes are opened with `Navigator.pushNamed` on the root navigator. A `--screen` widget is pushed on the root navigator in a `MaterialPageRoute`. The location the app shows afterwards is the screen's `landedOn` when it differs (a sign-in redirect).
2. **Text is drawn in the app's real fonts, which the harness loads from files before the first frame.** There are three sources, and each family is registered with `FontLoader`:
   - **Fonts bundled in `pubspec.yaml`** (`flutter: fonts:`) are loaded from their asset files under their family name.
   - **google_fonts families.** Motif downloads every weight and style a family has once into `motifHome()/fonts/google/<Family>/`. It gets them from the Google Fonts CSS2 API, asking for `ital,wght@0,100;…;1,900`; the API answers with only the faces that exist, and sends static TTF files to a client that doesn't claim WOFF2 support (`User-Agent: Mozilla/4.0`). google_fonts asks the engine for `<Family>_<variant>`, with the family's spaces taken out: `Onest_regular`, `Onest_italic`, `Onest_700`, `Onest_700italic`, and `ReadexPro_regular` for Readex Pro. The harness registers each file under that name, and registers all the files together under the plain family name, with and without its spaces (`Readex Pro`, `ReadexPro`), which google_fonts uses as its fallback. (Until Maktaba, Task 12, a family with a space was registered with it, so its text was drawn as boxes.) Before the app starts, the harness sets `GoogleFonts.config.allowRuntimeFetching = false`. The cache is guarded: a family name must be letters, digits, spaces and hyphens before it goes into a path or a request; each download must start like a font file (`00 01 00 00`, `OTTO`, `true` or `ttcf`); files are written to a temporary name and renamed, and the list of faces is written last, never empty. A family Google Fonts doesn't have, a failed or slow download (30 s per request) or a bad file gives a note, and the screenshots go on without that family.
   - **Roboto and `MaterialIcons`** come from the Flutter SDK's own copy (`<flutter>/bin/cache/artifacts/material_fonts/`). They are used for plain Material text and for icons. The SDK is found from the `flutter` command with links followed; if its `material_fonts` folder is missing, the run notes it (`flutter precache` fetches it). A pubspec font file that doesn't exist is left out with a note.

   The fonts work offline after the first run. A second run with the network blocked (a proxy that refuses connections) drew the same screenshots. Without the loaded fonts (the control run), every letter and icon was a box. Because downloading once worked, the other way (google_fonts fetching over real HTTP inside `tester.runAsync`) wasn't built. It would also need the network on every fresh machine and every CI run.
3. **`flutter test` has no system font fallback.** On a phone, a character that the chosen font lacks is drawn by a system font. Under `flutter test`, it is drawn as the font's empty box. The spike showed this: with Onest's `fontFamilyFallback` removed, Arabic text became boxes. Text renders when an Arabic font is in the style's `fontFamilyFallback`, as in Motif's generated `MotifTheme` (the Arabic companion font) and in the fixture. If a family isn't loaded at all, its text falls back to the test font's solid boxes.
4. **Sizes, safe areas, scheme and locale are set on the test view.**
   - Phones are `mobile-360` (360×800), `mobile` (390×844) and `mobile-430` (430×932). `tablet` is 768×1024. All four use device pixel ratio 2. `desktop` (1440×900 at ratio 1) is drawn only with `--sizes desktop`.
   - The size is set as `tester.view.physicalSize` (logical size × ratio) plus `devicePixelRatio`. Phones get an iPhone-like safe area through `padding` and `viewPadding`: 47 at the top and 34 at the bottom, in logical pixels, multiplied by the ratio.
   - Light or dark is set with `platformBrightnessTestValue`. The app's `ThemeMode.system` follows it.
   - The locale is set with `localeTestValue` and `localesTestValue`: `ar` for right to left. In the spike's hand-run, Arabic screens mirrored as expected.
   - The 390×844 size is checked by `flutter-render.test.ts` (780×1688 PNGs, light differs from dark). 360×800, 430×932, the tablet, the desktop size and Arabic were each rendered once by hand and looked at; no automated test covers them yet.
   - Every value is reset after each screenshot. `WidgetsApp.debugAllowBannerOverride = false` hides the DEBUG ribbon.
   - Under `flutter test` the target platform is Android, so screens use Material's Android look (Roboto, Android page transitions). Apple's system font can't be shipped, so an iOS look isn't attempted.
5. **A PNG is the root render view's layer.**
   - The root `RepaintBoundary` is the `RenderView`. Inside `tester.runAsync`, the harness calls `(view.debugLayer as OffsetLayer).toImage(view.paintBounds)`, which is how flutter_test's own `captureImage` works, then `toByteData(format: png)`, and writes the file with `dart:io`.
   - `paintBounds` is in physical pixels, so `mobile` gives 780×1688.
   - Waiting uses bounded pumps: one `pump()`, then `pump(100 ms)` while a frame is scheduled, at most 50 times (5 s of test time). It never uses `pumpAndSettle`, which never finishes while a spinner is showing.
   - Every screenshot calls `GoRouter.of(context).go(route)`, `/` included. The app's router is a global object, and it keeps the previous screenshot's location. The spike showed this: a `/` shot taken after `/settings`, without its own `go`, showed Settings. Other global state the app keeps also carries over from one screenshot to the next within a run.
6. **Timings, and the run's time limit.** Measured on the fixture (Windows 11, Flutter 3.44.8):

   | Run | Time |
   |---|---|
   | First run on a machine, in a fresh copy of the app (fonts downloaded, test compiled), 2 shots | 10.3 s |
   | First run in a fresh copy, fonts already cached, 2 shots | 9.5 s |
   | Later runs (`flutter test` reuses its compiled test), 2 shots | 3.2 s |
   | Later runs, 10 shots | 3.8 s |
   | Later runs, 40 shots | 5.5 s |

   Each screenshot after the first adds about 60–75 ms. The time limit Task 9 uses is **240 s plus 3 s per screenshot**. This is a judgement, not a measurement: the measured basis is the fixture's 9.5 s first compile and 60–75 ms per screenshot, on one Windows machine, with a small app.
   - The 240 s is about 25 times the fixture's first run, to allow for a real app with much more code to compile, on a slower CI runner. No real app was timed.
   - The 3 s per screenshot is about 40 times the measured cost, to allow for heavy screens and for two waits that each reach the 5 s cap (each pumped frame costs real time).

   When the limit is reached, the runner stops the whole process tree (`taskkill /T /F` on Windows; on other systems the run is its own process group, which is killed), waits at most 3 s more for its output and exit, and still deletes its files. Before a run starts, it deletes the previous `result.json` and the screenshots it is about to take, so a run that fails early can't return old pictures.
7. **CI on Linux uses `subosito/flutter-action@1a449444c387b1966244ae4d4f8c696479add0b2` (v2.23.0)** with `channel: stable`, `flutter-version: 3.44.8` and `cache: true`.
   - The action is pinned to a commit, like the other actions in `ci.yml`.
   - Flutter is pinned to an exact version for two reasons. The fixture's `pubspec.lock` was resolved by that SDK, which pins packages such as `clock` and `test_api`. Text drawing also changes between Flutter releases.
   - `flutter test` needs no display, so the same test should run headless on `ubuntu-latest`. This hasn't been run on Linux yet; the first CI job with Flutter will prove it.
   - Tests that need Flutter skip where it isn't installed (`hasFlutter`). The current matrix stays as it is until a job installs Flutter.

8. **States and the audit (Task 10).**
   - **State scripts.** A Flutter state is `design/states/<name>.dart`, defining `Future<void> motifState(WidgetTester tester) async`. `motif_hooks.dart` imports each one and runs it after the screen has opened; its screenshot is `<screen>@<name>…png`, after the plain one, as on the web. What it throws is the screen's error, tagged `State "<name>": …`, and the screenshot is still taken. A state that is still running after 15 s of real time (one waiting on the test's clock without pumping, or on something that never comes) is left behind with "it was still running after 15 seconds". The test body runs in flutter_test's fake-async zone, whose queued work runs only when something flushes it, which flutter_test does only while the test waits on `runAsync`. Motif can't wait with `runAsync` itself, since a script calling `runAsync` at the same moment would fail ("Reentrant call to runAsync() denied"). So while a state runs, a timer outside that zone checks the clock and flushes the queued work every 5 ms until the test ends. It only flushes: moving fake time on from there (`binding.delayed`) would run the rest of the screenshot inside that move, where the next `pump` fails with "Cannot elapse until previous elapse is complete". After the screenshot and its audit, a state left behind gets ten minutes of the app's clock (one `pump`), so the timers it waits on fire and flutter_test doesn't fail the test with "A Timer is still pending". A state stuck for ever inside its own `runAsync` isn't stopped; the run's time limit is what ends it. A state that pumps for ever (`pumpAndSettle` under an endless animation) ends at flutter_test's own limit with "pumpAndSettle timed out". It took a few seconds on the fixture, and the run then notes to use `tester.pump(const Duration(...))` instead. `runShot` checks every state for `motifState`, and every `--screen`, before it writes anything: a problem is a usage error.
   - **Setup has the same 15 s**, of real time or of the app's clock, whichever comes first. A setup that hasn't finished is the screen's error ("design/states/setup.dart didn't finish within 15 s."), not a start without it.
   - **The audit runs in the harness** (`motif_audit.dart`, written and deleted with the others) on the screen as drawn, and feeds the web's `audit.json` through the same `toFindings`. Which checks run on which screenshot is planned in TypeScript (`auditChecks`), as on the web: contrast and names on every screenshot; tap targets on phones and the tablet, in light; reduced motion once per look, in light at 390.
   - **Contrast is computed by Motif, not read from `textContrastGuideline`.** The guideline's verdict comes only as text (the semantics node and the colours' `toString`, whose format changed with wide-gamut colours), its colours are the most common light and dark pixels of a 1× picture (anti-aliased blends for small text, not the text's colour), and it finds text through `find.text(label)`, which misses a node that merges several texts. Motif walks every `RenderParagraph` and `RenderEditable` that is drawn (not offstage, not on a route under an opaque one, not transparent, clipped to its list): the foreground is the colour of most of its characters (with its `Opacity`/`FadeTransition` ancestors), the background a colour in the screenshot's own pixels under it, and the ratio WCAG's. The text's pixels are those on the line from the background to the text's colour as blended at its alpha (glyphs and their anti-aliased edges, within 6 of 255 in RGB distance), so faint text doesn't compete with its background and nearly invisible text is still found. The background is whichever of the three most common colours explains the most pixels that way, and it is used only when it covers at least half of the pixels that aren't the text's. Under a photo or a gradient no colour does, and the text is left out, as axe-core leaves it "incomplete" on the web, rather than judged against an arbitrary pixel, cut to two decimals as axe-core does. Large text is WCAG's (24 px, or 18.66 px bold), as axe-core judges it, where the guideline uses 18 and 14. Text in a disabled control is skipped. Colours are CSS hex.
   - **What the contrast check leaves out, and icons (Task 15 follow-up, from HiSalon's hands-on test).** On a real app the list was mostly noise; these four rules came from it.
     - *Icons are marks, judged at 3:1* (WCAG 1.4.11), not at text's 4.5:1. A paragraph is an icon when an `Icon` widget draws it (an `Icon` has no child, so a paragraph under one is its glyph), when all its characters are in a private use area (the Basic Multilingual Plane's, or planes 15 and 16, where HiSalon's icon font puts them), or when it is one or two characters in a family whose name has "icon" in it. Before, icons in the plane-0 area (Material's) were never judged, and those in planes 15 and 16 were judged as text and named by their glyph. A finding names an icon by the `Icon`'s `semanticLabel`, else by its code point (`Icon(U+E25B)` in the selector, `kind: "icon"`); after the run, Motif names Material and Cupertino icons from the SDK's own `icons.dart` (`Icons.favorite`), which it reads only when a finding is about an icon. A glyph is never printed. The web never reports the "icon" kind, so its wording is unchanged.
     - *Covered text isn't judged.* Only for text that fails: a hit test at three points on its middle line (a quarter, half and three quarters across). Hit tests run from the top down, the reverse of painting, so when the hit test reaches another branch before the text or a box the text is in, that branch is drawn over the text there. It covers the text if anything drawn in that branch paints at the point (a box with a colour, gradient or image, a `ColoredBox`, a `Material` with a colour, an image, other text, a blur, a custom painter): a floating tab bar, a dialog's barrier. The whole branch is looked through, not only the hit path, because a hit test enters only the topmost child at each level: HiSalon's glass tab bar paints its blur and tint in a layer under the tabs that take the taps, and a first version that looked only along the path still reported "Offers" under it. A branch that only takes taps (an `InkWell` laid over a card, a `GestureDetector`) paints nothing and doesn't count. Text under an `IgnorePointer` takes no hits, so it can't be told apart this way and is judged as before. Paint order was the other way; it would need each render object's own rules for which children it paints over which, and hit testing already encodes them.
     - *Text over an image the screenshot doesn't show isn't judged:* an `Image` that hasn't loaded, one the harness drew from its blank 1×1 picture (a request `http.json` doesn't answer), and a decoration's `NetworkImage` the harness answered blank. On a phone a photo is there. An image that loaded is judged by its pixels, as before (a photo has no single background, so its text is left out anyway).
     - *Text with no letters or digits isn't judged* (a "·" or "|" between two facts), as axe-core leaves such text "incomplete" on the web. One finding per screen for them was the other way, but it would report a mark nobody reads as text.
     - *A text's kind is its own.* A contrast finding is about a control (`button`, `field`) only when the text is that control's whole name (a button's label), or is a field's own text; text inside a tappable card is `element` ("Text "Manama""), where it was "The "·" button".
   - **Tap targets and names come from the semantics tree**: nodes with a tap or long-press action, not merged, not hidden, on screen. A node's size is that of the render box that made it (the node's own rect is cut where a list clips it); under 44×44 logical px is `target-mobile`. Links are left out of the size check, as Flutter's own guideline does (WCAG's inline exception). A node with no label, tooltip or value is `name`; for a text field (`field`, counted as an unlabelled input is on the web) its hint, the placeholder, also names it, as axe-core accepts a placeholder. A node covering 90% of the screen or more that isn't flagged a button, link or text field is left out of `name` (Task 15 follow-up): it is a gesture on the background, such as HiSalon's `GestureDetector` that closes the keyboard on every screen, not a control anyone aims at. A full-screen node that says it is a button is still reported.
   - **Motion**: after the screen has settled, with reduce motion on, the harness pumps two more seconds; if a frame is still scheduled, it records which elements rebuild in the next frame (`debugOnRebuildDirtyWidget`, or failing that what repaints, `debugOnProfilePaint`), and names the first widget worth naming at or above it. This differs from the web, where only movement counts (fades and colour changes are allowed): Flutter's frames don't say what changed, so any animation that keeps going is reported, a looping fade included. Telling movement apart (comparing where boxes are between two frames) was left out; a painted spinner, which moves without its boxes moving, would then be missed.
   - **Selectors** are the closest three widgets worth naming above the subject, then the subject, with a `ValueKey` as `#value` and its text: `AuditScreen > Scaffold > ListView > Text("Prices include tax")`. Widgets worth naming are public stateless and stateful widgets that aren't framework plumbing (a list in `motif_audit.dart`: `Material`, `InkWell`, `Scrollable`, `*Transition`, …). The subject is the outermost such widget no bigger than the problem (the `IconButton` around its `InkWell`), and never above the screen's or the app's edge (`Navigator`, `Overlay`, `Router`, `WidgetsApp`/`MaterialApp`/`CupertinoApp`, `View`). A tap area around the app's navigator (outside every screen) is named by the closest widget worth naming around it. Before (Task 15 follow-up), a full-screen tap area climbed to the app's root, and HiSalon's name finding said only `ProviderScope`; it now says `AppScope > TapToDismiss > MinApp > HandsOnScreen` for a full-screen button on a screen in the test.
   - **`--screen` checks a class is a widget** by what it extends. It must extend Flutter's or a common state package's widget base, or another class of the app that does. A base from a package Motif doesn't know is guessed by its name (ending in Widget, View, Screen or Page). Any other class is refused, with a pointer to `--routes`.
   - **No 24 px tap-target rule on Flutter.** On the web, axe's `target-size` (WCAG 2.2 AA, 24×24) runs at every size. Flutter has only the 44×44 `target-mobile` check on phones and the tablet, so at `--sizes desktop` a Flutter screen gets contrast and names only.
   - The semantics flags are read with the deprecated `hasFlag`, which every Flutter has; `flagsCollection` doesn't exist in older ones.
   - Measured on the fixture: 64 screenshots in 9 s without the audit, 128 (two variants) in 12 s with it.

## Consequences

- Motif can draw a Flutter app's screens with only the Flutter SDK: no emulator, no simulator, no Mac. This was proven on Windows with one small app; Linux and macOS, and apps with plugins, network calls or other routers, are for Task 9 and CI to prove. The cost is that the screens use Android's look.
- Motif must know which google_fonts families an app uses before the run starts. It finds them in the guide's font tokens and by scanning the app's code (and its in-repo path packages') for `GoogleFonts.<name>(…)`, `GoogleFonts.<name>TextTheme(…)` and `GoogleFonts.getFont('<Family>')`. It maps each method name to its family through the `asMap()` table of the google_fonts package that the app resolves (the app's `.dart_tool/package_config.json` locates that package; without it, Motif asks for `flutter pub get` and stops, as it runs pub get nowhere else). A family that's missed shows up as boxes, so the harness checks every `RenderParagraph`'s font families against the families it loaded and notes any it couldn't load. It also checks the fallback families (`fontFamilyFallback`) of text with letters beyond Latin (Greek, Cyrillic, Hebrew, Arabic, CJK, emoji; not punctuation, symbols or icons), since that is the text that draws from them, and notes a fallback it couldn't load with the screens it was on (Task 12 follow-up: an unloaded Arabic companion had made every right-to-left screenshot boxes with no note). Latin-only text never reaches its fallbacks, so its fallbacks aren't judged.
- With runtime fetching off, google_fonts still tries its own load. For each family it prints "unable to load font Onest-Regular … allowRuntimeFetching is false", although the text renders in the font Motif loaded. These lines are removed from the Flutter output Motif shows when a run fails.
- An app that relies on the phone's system fonts for another script (Arabic text in a Latin-only family with no fallback listed) gets boxes in its screenshots. Motif notes this instead of hiding it. Its own generated theme lists the Arabic companion as a fallback, so apps that use `MotifTheme` aren't affected.
- Screenshots in one run share the app's global objects (router, singletons, caches). Task 9 navigates explicitly for every shot. Its setup script (`design/states/setup.dart`) is where an app resets anything else.
- If `HTTP_PROXY` or `HTTPS_PROXY` is set, `flutter test` fails before any test starts. Its test listener connects to `127.0.0.1` through the proxy. Motif adds `127.0.0.1,localhost` to `NO_PROXY` and `no_proxy` for the run, keeping what was there.
- An app's network requests never leave the test (Task 9): `HttpOverrides` answers them from `design/states/http.json`, and anything unmatched gets 404 and a note naming it (an image gets a blank picture). Platform channels of `shared_preferences`, `flutter_secure_storage`, `path_provider`, `package_info_plus`, `connectivity_plus` and `url_launcher` are answered when the app resolves them; any other plugin's `MissingPluginException` becomes the screen's error, pointing at `design/states/setup.dart`. What the app throws while a screen draws is that screen's error, not the end of the run.
- The same app can give PNGs that differ slightly between operating systems (anti-aliasing). Motif's tests compare sizes and whether light differs from dark, not exact pixels.
- The font cache grows by about 0.8 MB for a family with nine weights (Onest). It is downloaded once per machine and shared by every app.
