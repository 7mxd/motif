# Motif 2.0: fair Test A pairs, "no access" state, left/right check

Date: 2026-11-18. Status: design approved in chat ("Go"), this document awaiting the owner's read.

## 1. Why

Test A on the release candidate 8dd1e1b (run 20261113-052637, 48 pairs) failed on the owner's votes: Motif 48%, it
needs more than 50% (AI judges 87% Motif / 3% baseline, a pass). The owner's comments show that the two sides of a pair
often show different things, not only different designs: each side invents its own sample data and its own mix of items
("the left option had more charts", emojis in one side's items). The owner's rule for a fair pair, in his words: "both
pages should capture the same idea, so that I can clearly decide": if one booking page shows buttons {A, A, A, A}, the
other must not show {A, B, A, C}.

A 60-second video the owner shared (notes and frames in `.superpowers/ideas/2026-11-18-ai-ui-video/`) lists three things
an AI-built screen misses: raw colours instead of design tokens, only the happy path (no empty, loading, error or "no
access" state), and left/right layout that breaks Arabic. Motif covers tokens already. It covers right-to-left in its
guidance and with `motif shot --rtl`, but nothing catches a fixed `margin-left` in the code, and "no access" is in none of
its state lists.

## 2. Goals

1. Both sides of a Test A pair show the same content: the same items, each item in the same situation with the same
   action, and the same key wording. The design is what differs.
2. A side that doesn't follow the content can be marked so by the owner while voting, and by the AI judges.
3. Motif's state lists include "no access" for screens that depend on who is signed in.
4. `motif check` flags fixed left/right layout, on all 9 stacks, where a start/end form exists.
5. One new full run (A+B+C+D) on the resulting commit, then the owner's vote, then the release checklist.

## 3. Non-goals and anti-goals

- No change to Test A's bar (decision 0014) or to the rubric's six design criteria. The 48% stays on record in
  `docs/test-a.md`.
- No automatic content check: it could only read web pages (no text layer in native screenshots), which breaks the
  parity rule. The owner judges content himself.
- No shared mock-data code file per stack.
- Anti-goal: content that favours one side. The Content part names nothing about Motif, design guides, tokens or
  components, and it is identical for the with- and without-Motif sessions (both copy the same `brief.md`).
- Anti-goal: skill text aimed at the briefs (rule: `cli/test/skill-text.test.ts`). The skill changes are general.
- Anti-goal: weakening any test, fixture or grader to get a pass.

## 4. Approaches considered

| Approach | Trade-off | Verdict |
|---|---|---|
| A. A "Content" part in each brief + a "didn't follow the content" mark on the vote page and for the AI judges | Works the same on all 9 stacks; relies on the judge noticing | **Chosen** (owner: "I would go with 'didn't follow the content' if I noticed that.") |
| B. A plus an automatic text check of each side's page | Only possible on web stacks | Rejected (parity) |
| C. A shared mock-data file both apps must import | Different file per stack; constrains code, not what the page offers | Rejected |
| Left/right as guidance only | Guidance already exists and gets skipped (the video's point) | Rejected; a `check` rule instead |

## 5. Design

### 5.1 The Content part of each brief

Each of the 10 briefs in `tests/fixtures/briefs/` gets a `## Content` section after "First screens". It fixes, per first
screen (welcome, sign-in, the third screen):

- **The items** shown: names, numbers, dates, people, amounts, in a fixed order.
- **Each item's situation and the action it offers**, with a mix, so a list screen shows at least three different
  situations (e.g. open → "Join", already joined → "Cancel", full → "Join waitlist").
- **Key wording**: the page title, the welcome page's main line and one supporting line, every button and link label,
  the sign-in fields and their labels.
- One line at the top: "Show exactly this content on these screens: no more items, no fewer, no other actions. How it
  looks and is laid out is up to you." Decoration, icons, images and layout stay free.

The content stays realistic for the brief's people and language. Arabic briefs (sahm, nabta, rihla, darb, …) give their
wording in Arabic where the brief's app is in Arabic. No emoji in the content (an emoji in an item would be content, not
design).

The welcome page's content stays short (a title, a supporting line, the call to action, at most three short points) so
it doesn't dictate the layout. Sign-in fixes its fields, its button label and its links (e.g. "Forgot password?", "Create
an account") so one side can't add or drop options such as "Keep me signed in".

Prompts in `tests/evals/cases.ts` don't change: both prompts already say to build what `brief.md` describes.

### 5.2 Marking "didn't follow the content"

**Owner vote page** (`tests/evals/page-a.ts`, `tests/evals/judge-owner.ts`): under each side, a quiet button "Didn't
follow the content". Pressing it saves the vote as a pick of the other side with `offContent: "left" | "right"` on the
vote (`OwnerVote.offContent?: Side`). Pressing both (both sides off) saves "same" with `offContent: "both"`. A plain pick
stays as today. The page shows the brief's Content part for the pair's screen in a fold under the images ("What both were
asked to show"), so the owner can check without remembering it. Existing votes files without `offContent` stay valid.

**AI judges** (`tests/evals/judge-a.ts`, `tests/evals/rubric-a.md`): the judge is also given the brief's Content part.
The rubric rule "Ignore differences in content that are just placeholder data" is replaced by: both designs were asked to
show the content below; a side that leaves out, adds or changes an item, an item's situation or action, or the key
wording loses the pair; if both do, judge the design as usual. The answer gains `"offContent": "left" | "right" | "both" |
"none"`. The six design criteria and their order don't change.

**Scoring and report** (`tests/evals/score-a.ts`, `tests/evals/report.ts`): a pick that comes from an off-content mark
counts like any other pick (the other side won). The report adds, per brief, how many pairs each kind of judge marked off
content, and for which side ("baseline 2, Motif 0"), so a pass that rests on content marks is visible.

**Vote page start-up**: the page waits for the vote server's first answer before it shows anything (that's why the
owner's phone showed a blank page on 2026-11-18). If no answer comes within 10 s, it shows "Still connecting… pull down to
reload; your votes are saved." instead of a blank page.

### 5.3 The "no access" state

Where Motif lists the states a data screen needs (`skill/modes/feature.md` step 4, `skill/modes/init.md` step on UX
patterns, `skill/modes/review.md` data-screen check, `skill/knowledge/visual-craft.md`, `skill/knowledge/anti-patterns.md`,
and each native/Expo adapter's `components.md` data-screen line), add: "no access, when what the screen shows depends on
who is signed in (a role, a team, a plan)". It is a state with its own message and a way forward (ask for access, switch
account, go back), not an error. Screens open to everyone don't need it. `skill/modes/review.md` treats a missing
"no access" state as a finding only for screens behind a role. Same wording rule as today: no tool names, no brief names.

### 5.4 The left/right check

A new `motif check` rule, id `physical-direction`, on all 9 stacks. It flags a fixed left/right where the stack has a
start/end form, with the start/end form as the fix:

| Stack(s) | Flagged | Fix |
|---|---|---|
| React web, plain web, Vue, Svelte, Angular (CSS, `style=`, Tailwind) | `margin-left/right`, `padding-left/right`, `border-left/right*`, `left:`/`right:` on positioned elements, `text-align: left/right`, `float: left/right`; Tailwind `ml-`/`mr-`/`pl-`/`pr-`/`left-`/`right-`/`text-left`/`text-right`/`border-l`/`border-r`/`rounded-l-`/`rounded-r-` | `margin-inline-start/end`, `inset-inline-start/end`, `text-align: start/end`; `ms-`/`me-`/`ps-`/`pe-`/`start-`/`end-`/`text-start`/`text-end`/`border-s`/`border-e`/`rounded-s-`/`rounded-e-` |
| React Native / Expo | `marginLeft/Right`, `paddingLeft/Right`, `left`/`right`, `borderLeftWidth`…, `textAlign: 'left'/'right'` | `marginStart/End`, `paddingStart/End`, `start`/`end`, `borderStartWidth`…, `textAlign` start via `writingDirection` |
| Flutter | `EdgeInsets.only(left:/right:)`, `EdgeInsets.fromLTRB`, `Alignment.centerLeft/…Right` and other left/right alignments, `Positioned(left:/right:)`, `TextAlign.left/right`, `BorderRadius.only(topLeft…)` | `EdgeInsetsDirectional`, `AlignmentDirectional`, `PositionedDirectional`, `TextAlign.start/end`, `BorderRadiusDirectional` |
| Compose | `absolutePadding`, `Modifier.absoluteOffset`, `Arrangement.Absolute.Left/Right`, `AbsoluteAlignment`, `TextAlign.Left/Right` | `padding(start=/end=)`, `offset`, `Arrangement.Start/End`, `Alignment.Start/End`, `TextAlign.Start/End` |
| SwiftUI | `.environment(\.layoutDirection, .leftToRight)` forced on a view; `Image(systemName:)` with a left/right chevron or arrow without `.flipsForRightToLeftLayoutDirection(true)` | remove the forced direction; add the modifier |

When it is a problem: Motif's design guide template already says "Layouts use start/end (not left/right), so
right-to-left languages work" (section 7). The rule reports violations when the project's `DESIGN.md` keeps a start/end
line in its accessibility section (any line naming both "start/end" or "start" and "end" with "left/right"). When the
developer removed that line, the hits are counted but not reported as problems, and `motif check` prints one line of
advice ("N places use left/right; if this app may be used in a right-to-left language, use start/end"). This replaces
the "only when the guide lists an Arabic-like language" call made in chat, because the guide has no language field and
the template line is what the guide actually promises. (Builder: owner to confirm, see §8.)

Exceptions: the existing `motif-ok` comment allows a deliberate physical direction (a slider's track, a map control, a
chart axis). Generated files (`motif.css`, theme files) are never flagged.

The skill's check-fixing guidance (each adapter's `checks.md`) gets the rule's row, so agents fix it during their own
verify step. The `--rtl` screenshot advice stays as the visual check ("check it with your own eyes").

## 6. Testing

- TDD for each part: unit tests for the rule per stack (each flagged form, each start/end form not flagged, `motif-ok`,
  generated files, the DESIGN.md line on/off); page-a tests for `offContent` votes and the 10 s note; judge-a/score-a/
  report tests for the new answer field and counts; skill-text tests keep passing (no brief names).
- Every contract fixture and seeded fixture (`tests/fixtures/*`) is run through the new rule. A hit in a contract
  fixture whose guide keeps the start/end line is a real finding: show the evidence to the owner before any fixture
  change (rule 15). A seeded fixture's new finding is reported to the owner the same way; it must not become a false
  positive in Test C by quietly editing the fixture.
- Fast suite locally (every test file except `fixtures-*` and `*e2e*`, ~830 s, in background) before pushing; CI green
  on all OSes on the PR.
- Then one full run (A+B+C+D, 49 cases) on the merged commit on the Mac (about a day), then the owner's vote.

## 7. Risks

- B and D grade "motif check finds nothing" (violations and warnings both count). Agents that use `margin-left` will now
  fail that criterion unless they fix it in their own verify step. This is real signal, but it can turn a passing case
  red; the run shows it.
- Fixing the content narrows what each side can show. If Motif's lead came partly from richer invented content, the
  owner's score could fall. That is the honest result the owner asked for.
- More fixed wording in Arabic briefs: wording must be natural; the owner can read it.

## 8. Calls made by Claude (for the owner to check while reading)

1. The left/right rule follows the design guide's own start/end line (on by default), instead of "only when an Arabic-
   like language is listed" as said in chat (the guide has no language field).
2. Both sides off content → the pair counts as "same" for the owner, and is judged on design for the AI judges.
3. The vote page shows the content in a fold under the pair.
4. The 10 s "still connecting" note on the vote page.
5. Content wording written by Claude for all 10 briefs, at least three item situations per list screen, no emoji.

6. Screen mapping: the Content section has one sub-heading per first screen, naming it exactly as the case names it
   (`### Welcome (/)`, `### Sign-in (/sign-in)`, `### <Name> (/<home>)` from `newApp`'s `home` in `tests/evals/cases.ts`;
   SwiftUI briefs use the `#Preview` titles the case uses). A pair's screen picks its sub-heading by that name; a pair whose
   screen has none gets no content (fold hidden, judge told nothing) and the run's preflight fails if a first screen has
   no sub-heading.
7. Scoring: an off-content vote counts in the owner's and AI judges' main figures like any pick; "both off" is a tie,
   the same as "same". The report lists off-content marks separately (§5.2).
8. Not-reported hits: when the guide has no start/end line, the rule's hits are `violation: false` and the advice line
   is not a warning, so they don't affect B/D's "motif check finds nothing". The rule needs the guide's start/end flag
   passed into `check` (new input; plumbing is the builder's).
9. Fixture discovery runs first: the plan's first task runs the rule over every fixture and pauses to show the owner any
   hit before anything else is built on it.
10. Web positions: `left`/`right` insets are flagged, except a symmetric pair in the same rule (`left: 0; right: 0`) and
    `50%` centring (`left: 50%` with `translateX(-50%)`), which mirror the same. Tailwind: the same for `inset-x-*`,
    `left-1/2`.
11. Generated files: the same list the `generated-edited` rule already treats as generated, per stack.
12. SwiftUI: `chevron.left/right`, `arrow.left/right` and their `.circle`/`.fill` variants without
    `.flipsForRightToLeftLayoutDirection(true)` are violations like the other forms (`backward`/`forward` symbols flip by
    themselves and are fine).
