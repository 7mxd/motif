# Motif 1.3: states that know their screens

Date: 2026-11-02. Branch: `v1.3`. First item of the 1.3 backlog from the job-tracker field trial.

## Why

`motif shot --state <script>` runs every state script on every screen the run captures: every page or screen, at every size, in light and dark, in every variant and, with `--rtl`, in both directions. A state belongs to one screen or a few: an Edit sheet lives on the application page, a Filter sheet on the list. Everywhere else the script finds nothing to do, and Motif still takes the screenshot.

In the third job-tracker run (Svelte 5, hash-routed, Motif 1.2.0) 10 states across 12 pages gave 1,200 shots, of which 990 were copies of a plain page labelled with a state's name. The run took 65 minutes. The copies also feed the audit (repeated findings) and the review (the agent looks through screenshots that show nothing new).

Flutter, Compose and SwiftUI build their shot lists the same way (`cli/src/stacks/{flutter,compose,swiftui}/shot.ts` cross every target with every state), and each native shot costs more (a test run, an emulator, a simulator), so they need it more. Expo goes through the web capture path (`cli/src/shot/capture.ts`) and gets the web behaviour.

The owner's direction: Motif should work out where a state belongs from the app itself, not ask the developer. Every stack Motif supports gets the same, complete behaviour. None is left for later.

## Who does what

Motif has two halves. The **skill** (the agent, guided by `skill/`) reads the app, its goal and its design, and writes the state scripts in `design/states/`. The **CLI** (`motif shot`) runs them and can't understand an app. The skill already knows, when it writes `edit.js`, that the Edit sheet is on the application page. 1.3 makes it write that down in the script, and makes the CLI follow it.

The developer does nothing: no lists to write, no flags to add, no scripts to edit by hand.

## Goals

1. **Each state runs only on its own screens.** A state script can name the screens it belongs to in a line near its top. `motif shot` runs that state only on those screens and takes no other shot for it, on every stack. On web the line names pages (routes as Motif captures them, including hash routes like `/#/applications`); on Flutter, Compose and SwiftUI it names routes or the `--screen` widget/preview names the run uses. The planned count Motif prints before a run, and the run's time, reflect only the shots it will take.
2. **A state can say "not here".** When a state's script runs on a screen and finds nothing to do (its button or sheet isn't there), it can say so, and Motif keeps no screenshot for that state on that screen and reports no audit findings for it. This is the safety net for a line that is wrong or out of date, and for scripts with no line. It works in every stack's state language: JavaScript for web and Expo, Dart for Flutter, Kotlin for Compose, Swift for SwiftUI.
3. **No state goes missing silently.** Two cases, told apart because one is a choice and the other a fault:
   - *Not in this run*: the state's line names no screen this run captures (the agent chose a few `--routes`, as `review.md`'s before/after steps do). A one-line note names the state and its screens. Exit status unchanged.
   - *Lost*: the state was tried on a screen its line names and said "not here" in every shot of that screen. The output names the state and the screen, says the line or the script is out of date with the app, and the run exits 1, as for a page that failed to render. A state with no line that says "not here" everywhere is lost the same way.

   A state captured at some sizes of a named screen and "not here" at others (a sheet that exists only on phones) is not lost; the JSON records which shots it skipped. The run's JSON result gains, per state, the screens it was captured on and the shots it skipped with the reason (`excluded`, `not-here`). The fields are additive; nothing existing changes shape.
4. **Old scripts keep working.** A state with no line runs on every screen, as in 1.2. The run adds one note listing such states and saying a line naming their screens would make the run faster. A script that returns nothing (or ends normally) is captured, as in 1.2.
5. **The skill writes the line and the "not here" answer, on every stack.** Every mode that writes or uses state scripts (`skill/modes/review.md`, `feature.md`, `init.md` where it applies) and every adapter's `checks.md` (plain-web, react-web, vue, svelte, angular, react-native, flutter, compose, swiftui, and `_template`) shows the line and the "not here" answer in that stack's own language. The skill picks the screens from the app's code and routes. When a review finds an existing state script without a line, it adds one as part of its normal work (job-tracker's 10 scripts get theirs on the next run).

## Decided

- **The line is a comment the CLI reads**, so it lives with the script and survives later runs. Name and grammar are my call: `// motif-screens: /#/applications/*, /#/matches/*`. The comment uses `//` in JavaScript, Dart, Kotlin and Swift alike. It's a comma list. `*` matches one path segment, so a route with an id (`/#/applications/42`) can be named without knowing the id. It sits in the script's leading region, which is comments, blank lines and, in Dart, Kotlin and Swift, `import`/`package`/`part`/`library` lines. The CLI reads only there.
- **Lines match the route as requested**, the string given to `--routes` or found by discovery, after trimming a trailing slash and ignoring any query string. They never match the address a page landed on. An `--rtl` look of `/` is still `/` even when the app sends it to `/ar`, so states follow their screen into every look.
- **"Not here" is per shot**, not per screen: a state can be present at phone width and absent at desktop width on the same page.
- **Web "not here" is `return false`.** My call. `return;`, `return undefined` and finishing normally all mean "captured", as in 1.2, so no existing script changes meaning. Today's guard `if (!target) return;` becomes `if (!target) return false;` in the skill's examples.
- **Native "not here" is a Motif-provided call that ends the state**, because `motifState` returns nothing in all three languages and its signature doesn't change. Each harness provides it (for example a `motifNotHere()` that throws a marker the harness catches) under a name idiomatic for that language; the harness treats it as "skip this shot", never as an error.
- **Filtering happens before the run where the stack allows it.** Native stacks build their shot list in TypeScript before the test runs: a state's line removes shots from that list, so they cost nothing. On web the CLI doesn't open a tab for a state on a page its line excludes.
- **`--states-only` with lines visits only screens that some state names**, so a states-only run of job-tracker opens only the pages with sheets. A state with no line still runs everywhere.
- **`--save` / `--against`:** a shot skipped on purpose (excluded by the line, or "not here") is not reported as missing from the run, nor as a failed comparison. A "before" set saved by 1.2 that holds copies compares only against the shots this run took; the extra "before" files are not reported as missing either.
- **Line problems are usage errors before anything runs**, as other `--state` problems are today: a malformed line, or a line naming a screen in a form that can't match (for example a native route on a web app). A well-formed line naming a screen that this run doesn't capture is not an error; it's goal 3's note.

## Non-goals (this step)

These are separate 1.3 items from the same trial, to be done after this one:

- A script that runs before every state (job-tracker's scripts each repeat the dev sign-in).
- Grouping tap-size findings by the short dimension, not the pixel value.
- Saying when a run without `--routes` resets `audit.json`.
- The 12-page cap.
- Sheet shots: backdrop covering only the first screen height; the focus ring left by a scripted click.

## Anti-goals (a failure even if it works)

- A state silently missing from a run, or from a review because its line was wrong.
- The developer having to write or maintain a list of screens.
- An existing script changing what it captures without the run saying why.
- One stack behaving differently from the others where the stacks could behave the same.

## Proof

- Unit tests per stack for the shot list and the web capture loop (line parsing, `*` matching, hash routes, `--states-only`, "not here", the missing-state note, the JSON result), next to the existing `cli/test/shot-*.test.ts`. Skill content tests (`cli/test/skill-content.test.ts`, `skill-modes.test.ts`, `adapters.test.ts`) assert every adapter and mode carries the line and the "not here" answer.
- The B/C/D evals on all stacks: Windows (web stacks, Expo, Flutter, Compose) and the Mac mini (SwiftUI, Vue, Svelte, Angular; Node 22.23.3 there). Same harness and pass bar as 1.1 and 1.2.
- A fourth job-tracker run with the dev build: the same 12 pages and 10 states, compared with the third run (1,200 shots, 65 min). Expected: about 200 shots and well under 15 minutes, every state captured on its own screen, no state missing.
- Docs: `motif shot --help`, README, `docs/parity.md`, release notes when released (asking the owner before any release, as for every post-1.0 release).

## Left to the builder

- Exact names for the native "not here" call in each language, and how each harness carries the skipped shots back in its result file.
- How the line's screens are matched against Flutter/Compose/SwiftUI targets (route vs widget/preview name) inside each stack's shot-list code.
- The wording of the notes, in the style of the existing `motif shot` notes.
- Whether the "no line" note lists states by name or counts them, so long as it fits on one line for a typical run.
