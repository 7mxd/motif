# Motif 2.0: character, built-in library, nothing to set up

- Date: 2026-11-08
- Status: Draft for the owner's approval
- Replaces: the 1.3.0 release (never tagged). 2.0.0 ships 1.3's state-screens work together with this.

## 1. Why

1.3.0's Test A (run 20261105-122429) failed on the owner's votes: the owner picked Motif in 35% of pairs (bar: more than 50%; v1.0 scored 65%). The AI judges passed it (77% Motif, 15% baseline). One brief, Sahm, was spoiled by a harness bug (fixed in PR #26). Even a perfect Sahm would only lift the owner's share to 45%, so the gap is taste, not tooling.

The owner's comments, per brief, show what the baseline had that Motif didn't:

| Brief | Owner (Motif/other) | What the owner said |
|---|---|---|
| Darb | 0/6 | "colorful and unique (with the 3D thingy)"; also "a bit greedy with being colorful" |
| Stride | 0/6 | other side has "better UX (more cards)"; Motif has "better UI" |
| Ledgerly | 2/4 | other side's landing "gives the user a full, complete experience" |
| Bloom | 2/4 | add motion to "Feed Lily" / "Water Monty"; desktop must not look like a phone view |
| Masar | 1/2 | Motif "looked a bit empty from the top" |
| Rihla | 1/2 | Motif's "lower part of the page is a bit empty" |
| Sanad | 4/2 | liked "This month" / "Fixers this week" cards; "I hate when I see the top menu bar full of options" |
| Nuzha 5/1, Nabta 2/1 | | Motif won |

Root cause in the skill: `skill/knowledge/character.md` sets the brand's loudness from the brief's personality words, and tells calm and business briefs ("Quiet business tools (invoicing, money, admin) keep their working screens plain") to stay plain. `skill/knowledge/anti-patterns.md` discourages gradients and glow everywhere. Motion is guided but not expected by default. Motif's screens came out correct, tidy and forgettable.

In the owner's words: colours, visuals and motion attract him; "any visual that look specially attractive or positively special and uncommon would go with my preferences". It "always depends on the tastes, opinions, and app theme".

Separately, Motif's optional design sources need setup: 21st.dev (key + MCP), Refero (paid plan + MCP) and 60fps.design (paid plan + MCP). The owner wants Motif to "look for best pieces suitable for the website, and work with nothing to look up". Eval runs have no sources connected (`no-mcp.json` is empty), so built-in content is also the only kind Test A measures.

## 2. Goals

1. **No screen is plain.** Every first-impression screen and every home/dashboard screen has at least one crafted, uncommon visual moment, whatever the brief.
2. **Fuller screens.** Home and landing screens show more of the user's own information as charts and stat cards, each one something the user would act on.
3. **No empty areas.** An empty band at the top or bottom of a screen counts as unfinished.
4. **Motion by default.** Charts draw in, numbers count up, lists stagger, key actions get a small press/feedback animation. The level of the approved mockup's option B is the default; calm themes turn it down; reduced-motion settings turn it off.
5. **A built-in library** of pieces for all 9 stacks, chosen automatically to suit the app. No MCP, no sign-up, no key, nothing fetched.
6. **Nothing to set up.** 21st.dev, Refero and 60fps.design are removed and replaced by built-in content.
7. **Pass Test A** on the owner's votes (more than 50% Motif on the briefs' average) while keeping the AI bar (≥70% Motif, ≤15% baseline) and decision 0014's floor.

## 3. Non-goals

- No redesign of the DESIGN.md + tokens contract or `motif check`.
- No new stacks.
- No change to how Test A is scored or judged (decisions 0013, 0014 stand).
- No runtime network fetches by Motif or by the agent following Motif.

## 4. Anti-goals (a failure even if tests pass)

- **The "C" look:** glowing charts, tilted 3D cards, heavy gradient backdrops, colour on everything. The owner rejected it ("C wouldn't be something I am looking for") and called Darb's version "greedy".
- Decoration that carries no information: every chart or card added for fullness must show the user's own data or a next action.
- A crowded top menu bar.
- Desktop layouts that are a stretched phone screen.
- Web getting the new look while native stacks get less (full-parity rule).
- Copying code whose licence forbids redistribution.
- Making a test pass by weakening a test, fixture, grader or judge prompt.

## 5. The approved direction (reference)

The owner compared three versions of a Ledgerly home screen (mockup: `.superpowers/brainstorm/phone/ledgerly-directions.html`, git-ignored, sent to the owner on 2026-11-08):

- A: today's Motif. Grey cards, one plain bar chart, no motion. Not chosen.
- **B: "Calm, but crafted". Chosen.** Quiet palette; one deep `brand` card holding the key figure with a drawn trend line; a progress ring on "Paid this month"; a coloured "invoices by age" segmented bar (current / 1–30 d / 31–60 d / 60+ d); overdue count in a status colour; everything animates in (line draws, segments grow). Owner: "B has more charts, which might be helpful." "The motion of option B is so good. Might be decreased, depending on the website theme, to make it more calm if needed."
- C: deep purple gradient backdrop, glowing area chart, tilted glass cards, rising gradient bars. Rejected.

B is the **floor for calm briefs**. Louder briefs go further (illustrations, bands, mascots, livelier motion), never into C territory.

## 6. What changes

### 6.1 Character guidance (`skill/knowledge/character.md`, `visual-craft.md`, `anti-patterns.md`)

- Replace "quiet business tools keep their working screens plain" with: every brief gets crafted moments; the brief's words set how loud, not whether. Calm/business briefs get B: one deep `brand` card per home screen, data drawn as small purposeful charts (trend line, progress ring, segmented breakdown), status colour for what needs action.
- Add a **fullness rule** for home/landing: show the user's own key figures and a breakdown, not one number and one chart. Each element must answer "what's happening" or "what should I do next".
- Add an **empty-area check** to the five-second test: a band of the screen with nothing in it (top under the header, bottom above the tab bar) fails the screen. Fill with content, a figure, an illustration or a closing call to action; never with filler.
- Keep the anti-patterns for gradients and glow, and name the C look explicitly as the limit. One subtle gradient remains allowed where the Direction calls for it.
- Add: top navigation keeps to the few destinations people use most; the rest goes in a menu.
- Desktop: home and landing get a real desktop layout (columns, side-by-side cards), never a centred phone column.

### 6.2 Motion by default (`skill/knowledge/motion.md`, each `adapters/<stack>/motion.md`)

- Default motion set, using the guide's motion roles: chart draw-in, number count-up, list/card stagger on first show, press feedback on primary and key actions, a small celebratory or confirming animation on a key action's success (e.g. "Feed Lily").
- A motion level from the theme: energetic/playful = lively, default = B, calm = reduced (shorter, fewer, no stagger), always none under reduced-motion settings.
- Each adapter gets the recipe in its native tool: CSS/Web Animations (plain web), Motion for React, Vue/Svelte/Angular built-ins (decisions 0011, 0012), Flutter implicit/explicit animations (flutter_animate is allowed where the project already uses it), Compose animation APIs, SwiftUI animations, Reanimated/Moti for React Native.

### 6.3 Built-in library (`skill/library/`, new)

A curated set of pieces Motif picks from, written as recipes the agent adapts to the guide's roles. Initial set (each for all 9 stacks):

| Group | Pieces |
|---|---|
| Charts | trend line (sparkline), progress ring, segmented breakdown bar, small bar chart with highlighted current period, stat with change indicator |
| Cards | key-figure brand card, stat row, "today's focus" card, item card with drawn thumbnail and labelled facts |
| Screens | landing hero variants by personality, welcome/onboarding, empty states with illustration, success moment |
| Motion | draw-in, count-up, stagger, press feedback, success confirmation |
| Visual accents | per-personality accent ideas (illustrated scene, shaped band, pattern), each with its loudness level |

Each piece states: what it's for, which briefs/personalities it suits, its loudness level (calm / default / loud), the data it needs, its states (loading, empty, error), its motion, and per-stack notes or code.

**Selection:** the skill matches pieces to the brief's personality words, the screen's job (UX pattern guides) and the motion level. The developer can ask for a different piece.

**Sources and licences:**
- Pieces are written by Motif. Where a permissively licensed source has a better idea, it may be adapted with its licence notice kept in the piece: Magic UI (MIT), Uiverse galaxy repo (MIT), flutter_animate (BSD-3), Moti (MIT).
- Excluded because their licences forbid redistribution or bundling: React Bits, Animate UI (MIT + Commons Clause), Aceternity UI (no redistribution as a library).
- Every adapted piece passes `motif check` once restyled to roles.

### 6.4 Design sources (`cli/src/sources/catalog.ts`, `connect.ts`, `doctor.ts`, `detect/sources.ts`, `skill/sources/`, `SKILL.md`, modes, README)

| Source | Change |
|---|---|
| 21st.dev | Removed. Replaced by the built-in library. |
| Refero | Removed. Replaced by built-in reference notes in the UX pattern guides: what strong apps of each kind put on welcome, home, list and detail screens. |
| 60fps.design | Removed. Replaced by built-in motion recipes (6.2), SwiftUI included. |
| Motion (motion.dev) | Kept as an optional extra (free, no account). Motif works fully without it. |
| Supahero | Kept (public gallery, nothing to connect). |

- `motif connect` offers only Motion. `motif connect 21st|refero|60fps` prints that the source is retired in 2.0 and that Motif now has it built in, and exits without error.
- `motif doctor` reports a still-configured retired source as "retired: you can remove it from <agent>'s settings", never as an error.
- SKILL.md's sources line becomes: "Built in: library, motion recipes, reference notes · Optional: Motion".
- Hairline (`@lucasmarkes/hairline`, MIT, React + plain web only) is mentioned in the react-web and plain-web adapters as an optional install for a landing page that wants a striking visual. It is not part of the core library, because native stacks can't use it.

## 7. How we'll know (success)

1. Unit tests in `cli/test/` for every skill-text rule added (same pattern as `skill-modes.test.ts`) and for the sources changes (`catalog`, `connect`, `doctor`, `sources` tests updated, none weakened).
2. CI 13/13 green on Windows, macOS and Linux.
3. A full eval run on the Mac (`--model claude-opus-5-5 --judge-model claude-opus-5-5`, `--work ~/ev-work`): B, C and D pass as in run 20261105-122429.
4. Test A: AI ≥70% Motif / ≤15% baseline, owner >50% Motif on the briefs' average, no brief lost outright (decision 0014). The owner votes blind; nobody votes for him.

**Gate and stop rule.** Test A is a hard gate for 2.0.0 (`docs/release-checklist.md`). If it fails, stop and show the owner the results and comments before any further round; the owner decides whether to tune and re-run. Never ship on the AI bar alone.

## 8. Constraints

- Full parity across the 9 stacks.
- All values from the guide's roles; `motif check` passes.
- Accessibility: contrast, tap targets, reduced motion, charts with a text alternative (the key number in words).
- Branch + PR for every change; no direct pushes to main.
- No secrets in any file.

## 9. Left to the builder

- The exact file layout inside `skill/library/` and how pieces are indexed for selection.
- How many visual-accent ideas per personality (at least one per preset in `skill/presets/`).
- Exact motion durations, within the existing motion roles.
- Order of work, as long as the sources removal and the guidance changes each land with their tests.

## 10. Calls made while writing (Claude's, for the owner to check)

1. **"The user's own data" for apps without numbers** (Darb meetups, Rihla trips, Masar routes): the app's own content counts: next meetup, upcoming trip, saved routes, people involved, counts and progress. Fullness means more of that, not invented charts.
2. **Library depth:** every piece has the same depth on all 9 stacks: the shared spec, then per-stack notes naming the native tool and the key code (short snippet where the native API is non-obvious). No stack gets a thinner version (parity).
3. **Library tests:** a structure test in `cli/test/` checks each piece has its fields (purpose, fits, loudness, data, states, motion) and a section for each of the 9 stacks. No new render tooling; pieces are proven in use by the eval runs.
4. **Dependencies:** a recipe uses only what its adapter already allows. Optional libraries (flutter_animate, Moti, Motion for React) only when the project already has them; otherwise the stack's built-in animation APIs.
5. **Retired sources:** `motif connect <retired>` exits 0, prints the notice and changes nothing; `motif doctor` reports only; no user settings are edited or deleted.
6. **Hairline:** a short optional mention in the react-web and plain-web adapters; not required for the release.
